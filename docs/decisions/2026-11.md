### D-1122-01 Google 연결은 회사가 넣은 OAuth 클라이언트로, 서버 브라우저에서 한 번에 한다
- **결정**: 운영 Lite에서 메일 연동(Google OAuth)을 지원한다. OAuth 클라이언트 값은 Lite 관리 화면에 회사별로 저장한다. 연결은 서버 브라우저 안에서 하고, Google이 거절하면 휴대폰에서 연결한다.
- **원인(확인한 것)**: 운영에는 Lite의 Google OAuth 값이 없었다. 운영 로그인(Supabase Google 제공자)과 개발용 `.env`는 같은 GCP 클라이언트(「Process GPT Lite (web)」, 동의 화면 내부용)를 쓰지만, 이 맥에는 운영 클러스터에 Secret을 넣을 권한이 없다. 연결 흐름도 운영과 맞지 않았다. 콜백에서 Google 계정 이메일로 로그인했고, 리디렉션이 www 주소에 고정되어 있었으며, 상태 쿠키 경로가 `/lite`를 뺀 경로였다.
- **세부(위임 판단)**:
  - Google OAuth 토큰만으로는 서버 브라우저가 Google에 로그인되지 않는다. 그래서 「OAuth 가 되면 NotebookLM 도 된다」를 이루려면 OAuth 동의 자체를 서버 브라우저에서 해야 한다. 그러면 한 번의 로그인으로 메일 토큰과 서버 브라우저의 Google 로그인이 함께 생긴다. 휴대폰 연결은 메일만 연결한다.
  - 회사 클라이언트는 보관함의 봉투 암호화를 적용해 회사 주체 아래에 저장한다. 기존 보관함 테이블에는 외래 키가 없어 운영 SQL이 필요 없다. process-gpt의 `tenant_oauth`(회사별 Drive 연동, secret 평문)는 쓰지 않았다.
  - 연결은 로그인한 사람에게 붙는다(Google 이메일이 달라도). 상태는 메모리에 저장하고, 회사 주소 공개 경로의 쿠키와 묶어 위조 연결을 막는다.
  - 새 Client ID를 넣을 때는 그 secret도 함께 받는다(병합 전 코드 검토에서 찾음).
- **2번과의 관계**: 대신된 작업을 deepagents가 멈추지 못하는 문제(D-1121-09, `/chat/stop` 403)는 Google 인증과 별개다. 에이전트 서비스의 방 소유 확인 문제라 결정 대기로 남긴다.
- **상태**: 구현 · 시험 완료(가짜 Google로 단위 8 · e2e 7 · 게이트웨이 e2e 3). 운영에서 사람이 할 일: GCP 클라이언트에 `https://uengine.process-gpt.io/lite/api/auth/google/callback` 등록, 관리 화면에 값 넣기. Google이 서버 브라우저 로그인을 받아 주는지는 그 뒤 실제로 로그인해 확인한다.

### D-1121-08 방 규칙과 NotebookLM 작업을 운영에 낸다 — 규칙은 그 방의 안내 메시지에 둔다

- **원인**: 11-04에 만든 방 규칙 · NotebookLM 안내 · 작업 독 · 직접 제어 로그인 수정이 병합되지 않은 브랜치(`feat/followup-habits`)에 있어 운영에 반영되지 않았다. 녹화의 문장 형태(「내가 주는 url이 있으면」)는 그때의 낱말 필터로도 잡아내지 못했다.
- **세부(위임 판단)**:
  - 11-04 구현에서 방 규칙과 브라우저 부분만 main으로 옮긴다. 후행 습관 · 가드레일 · 팀 맥락은 옮기지 않는다.

  - 사용자 지시에 따라, 1차 구현의 정규식 거르개 · 링크 밖 30자 규칙 · 이름 고치기 · NotebookLM 낱말 지름길을 걷어냈다. 사이트 지식(NotebookLM 순서)은 `skills/notebooklm/SKILL.md`로 옮겼다.

### D-1121-09 바로잡는 말로 시작한 사이트 작업은 같은 방의 앞 작업을 대신한다
- **결정**: 「뒤에서 돈 작업이 먼저 끝난 것 같아요」, 「노트북 lm을 이용한게 아니고 그냥 가져와서 그냥 만들어 버렸습니다」 — 바로잡은 뒤에는 앞 작업이 기존 방식으로 끝나 「완료」를 내면 안 된다.
- **세부(위임 판단)**:
  - 프로젝트 방은 대화가 하나이므로, 같은 방에서 새 사이트 작업이 시작되면 앞 에이전트 작업을 멈추고 「notebook.google.com에서 하는 브라우저 작업으로 바꿔서 이전 작업은 멈췄어요.」처럼 이유를 남긴다. 기다리던 작업은 에이전트 서비스에 보내지 않는다.
  - 메인 채팅은 여러 일이 동시에 진행된다. 그래서 「진행 중인 요청을 바로잡는 말인가」를 판정하고, 0.7 이상인 그 작업 하나만 멈춘다.
  - 링크 없이 바로잡는 말은 라우터 모델이 대화 기록을 보고 할 일(앞서 올린 링크 포함)과 브라우저 스킬을 정한다. 첨부는 메시지 종류로만 찾는다.
  - 새 프로젝트는 모델 제목을 기다리지 않고 바로 만든다(「시작이 안되네요」, 「반응이 많이 힘들네요. 하고 있다는 느낌을 주든지 해야 될 것 같구요」). 응답은 20초 안팎에서 30ms 안팎으로 줄었고, 화면은 보내자마자 내 메시지와 진행 표시를 보여 준다.
- **함께 찾은 결함**: deepagents가 Lite 대화의 `/chat/stop`을 403으로 거절한다. SDK가 `chat_rooms`로 방 소유자를 확인하는데 Lite 대화는 그곳에 없다. 그래서 「멈추기」와 이번 「대신하기」는 화면의 스트림만 끊고, 에이전트 서비스의 턴은 끝까지 실행될 수 있다. 화면에 「완료」는 더 나오지 않는다. 고치려면 SDK와 deepagents를 따로 배포해야 해서, 아래 결정 대기 항목에 둔다.
- **상태**: 구현 · 시험 완료. 실제 BFF에서 녹화 상황 그대로 재현했다(앞 턴이 이유 문구로 끝나고 「완료했습니다」가 없음). 운영 반영 — PR #4(28d75bc), 배포 e9b23d3.

### D-1121-10 브라우저 작업이 멈추면 무엇이 필요한지와 할 일을 말하고, 로그인은 사람이 한 번 한다
- **결정**: 「어쨌든 인증문제든 뭐든 사용자에게 조치가능하게 올바른 오류 메시지가 나온건 아님」 — 녹화 끝의 「확인 필요」[확인 필요]만으로는 무엇을 해야 할지 알 수 없었다.
- **원인**: NotebookLM은 서버 브라우저에서 구글 로그인이 필요하다. Lite의 「Google로 계속하기」는 Lite 계정 확인일 뿐, 서버 브라우저에 구글 쿠키를 주지 않는다. 휴대폰에서 다시 인증해도 풀리지 않는다. 게다가 운영 서버 브라우저는 프로필을 컨테이너 안에 두어, 배포할 때마다 로그인 정보가 지워졌다.
- **세부(위임 판단)**:
  - 작업 카드에 `need`(login · blocked · captcha · choice · approve · stuck · other)와 `reason`(멈춘 이유와 할 일)을 넣는다. 알약은 「로그인 필요 · <사이트>」처럼 말하고, 카드에 이유 전체와 크게 표시한 첫 번째 단추(직접 로그인 · 직접 확인 · 멈추기 · 다시 시도)를 둔다. 휴대폰에서 그 부분이 입력창 아래로 숨지 않게 한다.
  - 막힌 화면은 새 페이지마다 모델이 한 번 판정한다(로그인 필요 · 거절 · 사람 확인 · 문제없음, 0.7). 로그인이 필요하면 모델 턴 없이 바로 사람에게 넘기고, 로그인을 마치면 저절로 이어진다. 녹화에서는 이 화면에서 몇 분 동안 「클릭 중」이었다. 사이트 이름은 페이지 자체에서 가져오고, 안내 문구는 사이트와 상관없는 일반 문장이다. 사이트 주소 · 문구 패턴으로 가리던 1차 구현은 사용자 지시로 걷어냈다.
  - 구글이 서버 브라우저의 로그인을 거절하면 그렇다고 알리고, 휴대폰이나 PC의 NotebookLM에서 만든 파일을 올리는 방법을 안내한다. 자동화 탐지를 피하는 설정은 쓰지 않는다.
  - 프로필은 영속 볼륨 `/data/browser-profiles`(`PRO_BROWSER_PROFILES`)에 두고, 이전 파드가 남긴 잠금 파일을 정리한다. 디스크 캐시는 50MB로 제한한다.
  - 「클릭을 어디다가 쓰고 있는지 그런 것들이 보이지가 않죠」: 누르기 · 입력 직전에 `browser.click`을 보내 실시간 화면의 해당 자리에 물결 원을 그린다. 알약은 「「새 노트북」 누르는 중」처럼 요소 이름을 말한다. 같은 화면에서 헛돌면 5턴째에 사람에게 넘긴다.
  - 「생성된 mp3 파일은 어떤 식으로 플레이어를 제공해 줄지」: 소리 파일 카드 아래에 바로 재생되는 플레이어를 둔다.
- **상태**: 구현 · 시험 완료. 실제 모델 판정으로 NotebookLM 첫 화면은 로그인 필요 0.95(약 2초), example.com은 문제없음 0.98이었다. 합친 서버에서 녹화 순서대로 링크를 주자 6초 만에 「로그인 필요 · Gemini Notebook」 카드가 떴고 모델 턴은 0이었다(이름은 페이지 제목). 구글이 서버 브라우저 로그인을 받아 주는지는 운영에서 사람이 로그인해 봐야 안다. 운영 반영 — PR #4(28d75bc), 배포 e9b23d3.

### D-1121-01 홈 알림 카드는 휴대폰 폭에 맞추고, 옆으로 밀어 닫는다
- **결정**: 「닫기를 할 때 좀 부드럽지 않게 닫아지는 문제가 있습니다」 — 홈 알림 카드를 닫을 때 화면이 흔들리지 않아야 한다.
- **원인**: process-gpt 채팅 알림의 제목에는 에이전트의 답 전체가 ```json 블록까지 그대로 들어온다. 공백 없이 이어진 긴 instance_id 때문에 카드가 휴대폰보다 넓어졌다. 그래서 홈 전체가 손가락을 따라 옆으로 밀렸고, 닫기(✕) 단추는 화면 밖에 있었다. 닫는 동안에는 닫히는 카드의 폭이 줄면서 아래 카드들이 왼쪽으로 105px 밀렸다(시험 F-MR-02로 재현).
- **세부(위임 판단)**:
  - 카드 제목은 두 줄까지만 보여 준다. 코드 블록, 글 끝의 JSON, 마크다운 표시는 제거하고, 긴 식별자는 카드 안에서 줄을 바꾼다. 홈 목록은 가로로 스크롤되지 않게 한다.
  - 휴대폰 알림처럼 카드를 옆으로 밀어서 닫을 수 있게 한다. 카드 폭의 1/3 넘게 밀면 닫히고, 그보다 짧게 밀면 제자리로 돌아온다. 손가락 동작이 ✕ 단추 위에서 시작하면 단추를 누른 것으로 본다. ✕ 단추는 그대로 둔다.
  - 닫히는 카드는 폭을 유지한 채 흐려지고, 아래 카드는 제자리에서 위로 올라온다.
- **상태**: 구현 · 시험 완료(F-MR-01~03). 운영 반영은 아래 상태 줄에 적는다.

### D-1121-02 루틴 화면을 열 때 이전 대화를 보여 주지 않고, 왼쪽 위 ‹로 연 곳에 돌아간다
- **결정**: 「이거는 닫기 자체가 안되네」, 「꿈뻑 하면서 아까 보셨던 것처럼」 — 홈 카드로 연 루틴 화면은 깜빡이지 않고 열려야 하며, 닫을 수 있어야 한다.
- **원인**: 루틴 정보가 오기 전까지 화면 가운데에 메인 채팅이 그대로 보였다. 응답이 느리면 그 채팅이 몇 초 동안 남았다. 휴대폰 상단 탭은 가로로 스크롤되어 루틴 탭을 가운데에 두므로 「홈」 탭이 가려졌다. 왼쪽 위 단추(≡)는 루틴 목록으로 가는 단추라서 사용자가 홈으로 돌아갈 방법을 알기 어려웠다(녹화에서는 「채팅」 탭을 눌렀다).
- **세부(위임 판단)**:
  - 루틴을 여는 동안에는 「루틴 여는 중…」만 보여 준다. 열지 못하면 사유와 「다시 시도」 · 「닫기」를 보여 준다. 기다리는 동안 다른 화면으로 이동하면 늦게 도착한 응답은 버린다.
  - 휴대폰 루틴 화면의 왼쪽 위 단추를 ≡(목록)에서 ‹(닫기)로 바꾼다. 누르면 연 곳(홈 · 채팅 카드 · 목록)으로 돌아간다. 주소로 바로 열어 돌아갈 곳이 없으면 루틴 목록으로 간다. 루틴 목록은 상단 「루틴」 탭으로 연다.
  - 휴대폰의 뒤로 가기 제스처에는 브라우저가 이미 전환 효과를 표시한다. 이 경우(hasUAVisualTransition)에는 앱의 흐려졌다 나타나는 효과를 중복 적용하지 않는다.
- **상태**: 구현 · 시험 완료(F-MR-04 · 05).

  - 설정은 배포(데이터베이스) 전체에 하나만 둔다(`membership_settings.require_approval`, 기본값 켬). 한 데이터베이스를 여러 회사가 함께 쓰므로 회사 관리자는 바꿀 수 없고, SQL Editor나 서비스 롤로만 바꾼다.

  - 설정이 바뀌면 정책 식 자체를 바꾼다. 정책 식에 하위 쿼리를 넣으면 `users`의 UPDATE 정책이 무한 재귀 오류로 작동하지 않는다(로컬에서 재현). 하위 쿼리를 그대로 넣었다면 설정이 끔인 상태에서도 사용자가 자기 정보를 고칠 수 없었다.
- **운영 DB에서 확인한 다른 점과 처리**:
  - 운영에는 `current_user_role()`·`get_role_level()`이 없다. `get_role_level()`은 새로 만들었다.
  - 운영에는 기존 가입 트리거가 항상 「대기」 상태로 행을 추가하는 `signup_requests` 테이블이 있었다. 대기 중인 93건은 3월부터 11-14까지 쌓였으며 한 번도 처리되지 않았다. 열 구성이 같아 테이블을 그대로 사용하고, 대기 중인 건은 승인 처리했다(`system:approval-off`).

### D-1118-01 업무와 프로세스는 그 인스턴스 화면에서 연다
- **결정**: 업무가 들어오면 홈 알림으로 알리고, 알림을 열면 프로젝트의 해당 인스턴스 화면으로 이동한다. 전체 채팅에는 덧붙이지 않는다. 이렇게 하면 해당 업무의 맥락에 맞게 걸러진 화면을 보여 줄 수 있다. 채팅이나 메일에서 프로세스가 시작될 때도 같은 방식으로 해당 인스턴스로 연결한다.
- **세부(위임 판단)**:
  - 내 단계: 프로세스를 시작한 채팅에 양식 카드를 붙이거나 전체 채팅에 「입력이 필요해요」 줄을 붙이던 동작을 없앤다. process-gpt 알림으로 생성된 홈 카드를 열면 인스턴스 화면으로 이동한다. 프로세스가 끝나면 전체 채팅에 줄을 추가하는 대신 홈 카드(「완료 · …」)를 띄운다.
  - 채팅 카드에서 시작: 시작하면 해당 인스턴스 화면으로 이동한다. 채팅의 카드는 「시작됨 ›」 링크로 남는다.
  - 메일로 시작(정식 등록 프로세스): 메일과 처리 안내는 인스턴스 화면의 대화에 남기고, 홈 카드 「메일로 시작 · …」를 띄운다.
  - 예약 실행: 실행 표시는 인스턴스 대화에 남기고, 홈 카드 「예약 실행 · …」를 띄운다.
  - 「내 할 일」 질문: 할 일마다 양식 카드를 붙이지 않고 하나의 목록으로 답한다. 목록의 항목을 누르면 해당 인스턴스 화면이 열린다.

### D-1111-12 인스턴스의 칸반 · 산출물 · 액티비티를 읽기 쉽게
- **결정**: 칸반을 다른 화면처럼 차분하게 바꾼다(「여기 UI도 약간 조금 어색해요 … 좀 자연스럽게 바꿀 필요가 있어요」). 산출물 탭은 폭을 활용해 내용을 보여 주고, 내용이 없으면 없다고 표시한다(「내용이 없으면 없다고 나오는 게 좋겠죠」, 「폭을 사실 낭비하고 있거든요. 좀 더 보여주게 하든지」). 액티비티는 반려로 되돌아간 흐름을 혼동 없이 보여 준다(「이것도 좀 헷갈리는데」).
- **세부(위임 판단)**:
  - 칸반: 카드는 모두 흰색 바탕에 왼쪽 상태 띠를 두고, 열은 같은 바탕에 상태 점을 둔다. 같은 구성 요소를 쓰는 할 일 목록 칸반도 같이 바뀐다.

### D-1111-13 음성 입력은 팝업 없이 폼에 바로
- **결정**: 업무 화면의 음성 입력을 팝업(「음성 에이전트」) 대신 화면 안에서 한다(「저렇게 팝업이 떠서 동작할 일이 아니죠. 여기에 그냥 묻혀서 들어가 있으면 될 문제입니다 … 거기에서 나올 만한 데이터가 여기 그냥 같이 들어와서 여기 입력되면 되는 거죠」).
- **확인한 원인**: 팝업은 OpenAI Realtime 프록시(react-voice-agent)를 쓰는데 운영 매니페스트에는 이전 이미지(`:latest`)가 지정되어 있고 실행 수가 0대로 설정되어 있다. 새 Realtime API 수정 사항은 운영 설정에 반영된 적이 없다. 오류는 화면에 보이지 않아 「연결됨」만 떴다. 입력창 옆 마이크는 들은 말을 보여 주지 않고, 멈추면 말을 언어 모델로 다시 작성해 모든 칸을 새로 만들고 자동 저장했다.
- **세부(위임 판단)**:
  - 마이크를 누르면 머리글 아래에 한 줄짜리 녹음 막대(경과 시간 · 들은 말 · 멈춤)를 표시한다. 받아쓰기는 휴대폰 웹에서 쓰던 기능(completion의 업로드 받아쓰기)을 함께 쓴다.
  - 칸이 하나뿐인 폼은 들은 말을 그대로 덧붙인다(언어 모델 없이). 칸이 여럿이면 「에이전트에 맡기기」와 같은 서버를 한 번 호출해 말한 칸만 채우고 나머지는 그대로 둔다. 저장 · 제출은 사람이 한다.
  - 코드 검토 뒤: 말로 채우는 동안 사람이 고친 칸은 건드리지 않고 안내에 적는다. 한 줄 칸은 말한 값으로 바꾸고(「고객명은 한빛물산」은 바꾸라는 뜻), 여러 줄 칸은 이미 쓴 글을 다시 쓰지 않고 새로 말한 내용만 새 문단으로 덧붙인다.
  - 팝업 진입 경로(⋯ 메뉴, 휴대폰 🤖)를 없앤다. 운영의 음성 프록시 배포(0대 · `:latest`)를 수정하거나 중단하는 일은 이 화면과 무관해져 따로 남긴다.

### D-1111-06 맡긴 업무에 필요한 전문 에이전트를 스스로 골라 붙인다(팀 구성)
- **결정**: 「이런 스마트한 티밍 단계가 있는가?」에 대한 답은 「없었다」이다. 기존 기능을 재사용해 팀 구성 단계를 새로 둔다. 기본으로 딥 에이전트에 맡기고, 꼭 필요할 때만 에이전트 프로필(스킬 · MCP 묶음)을 서브 에이전트로 붙인다.
- **세부(위임 판단)**:
  - 프로세스 설계자가 해당 단계의 에이전트 · 도구를 정해 두지 않은 업무에서만 고른다. 정해 둔 팀은 그대로 쓴다.
  - 후보는 같은 회사의 에이전트 프로필(스킬 · MCP 묶음)이다. 다른 방식의 에이전트(a2a 등)는 뺀다.
  - LLM이 한 번 고른다(최대 3개). 채팅방 라우터는 거의 늘 누군가를 고르지만, 여기서는 그 스킬 · 도구가 꼭 필요할 때만 고른다. 필요 없으면 혼자 처리한다.
  - 고른 뒤 실제로 맡길지는 딥 에이전트가 일하면서 정한다. 화면의 「팀 구성」 카드에 누구를 왜 골랐는지(또는 혼자 처리) 남긴다.
  - 확인(설치본): 제안서 파일이 필요한 업무에서는 「제안서 문서 작성 에이전트」만 골라 실제로 맡겼다. 고객 요청 입력 업무에서는 혼자 처리했다.
- **함께 고친 결함**: 이전 단계 입력이 짧아 그대로 전달됐는데도 「파일로 저장되었다」고 안내해, 에이전트가 없는 파일을 찾다가 결과 없이 끝났다.
- **상태**: 반영 — deepagents #12(모든 테넌트에 함께 적용, 끄는 설정 DEEPAGENTS_AUTO_TEAM=0)

### D-1111-07 휴대폰에서는 「내 일」만 처리한다
- **결정**: 휴대폰 사용성 점검(별도 에이전트, 화면안 7개) 결과에 따라 진행한다. 휴대폰에는 할 일 · 진행 · AI · 알림 · 나만 남기고, 관리 기능은 아예 두지 않는다(「모바일에서는 모든 기능을 사용할 필요가 없어. 특히 관리자 기능은 아예 필요가 없고」, 「준 안대로 구현 진행해」).
- **세부(위임 판단)**:
  - 1단계: 휴대폰(라이트 버전)에서 관리 · 설계 · 분석 메뉴를 숨기고, 주소로 들어와도 「PC에서 열어 주세요」 안내 화면으로 보낸다. 관리자도 휴대폰에서는 같은 화면을 본다. 바로 고칠 결함 세 가지(휴대폰에서 숨겨진 에이전트에 맡기기, 저장되지 않던 AI 초안, 미리 선택돼 있던 「승인」)도 고친다.
  - 2단계: 하단에 탭 다섯 개가 있는 화면을 만든다. 저장소에 이미 있는 휴대폰 앱(mobile/)을 쓸 수 있는지 하루 동안 확인한 뒤 방식을 정한다.
  - 휴대폰 기본 화면은 새 화면을 적용한 뒤 라이트 버전으로 바꾸고, 「나」 탭에 「PC 화면으로 보기」를 둔다. 그때 D-1111-02(데스크톱 기본)를 뒤집는다.
- **2단계 방식(위임 판단)**: 저장소의 휴대폰 앱(mobile/)을 휴대폰 웹(/m/)으로 쓴다(A안). 하루 확인에서 고치지 않고 브라우저에서 돌았고, 서빙은 약 60줄, 첫 로딩은 포털의 7MB 이상 대신 약 1.5MB다. 지금 화면을 손보는 B안과 일수는 비슷하지만 PC 화면 회귀 위험이 작다.
- **상태**: 휴대폰 기본 화면은 D-1111-09에서 다시 데스크톱 화면으로 바꿨다. 1단계 vue3 #248, 2단계 vue3 #249(아래 탭 다섯 칸 · 업무 상세 · 승인 화면 · 진행 타임라인 · 알림 · 나, 휴대폰 기본을 휴대폰 웹으로). 남은 것: 반려 · 승인 · 에이전트 완료 알림은 서버가 아직 만들지 않음, AI 답의 할 일 카드, Word · HWPX 미리보기, 실제 휴대폰 확인


### D-1111-08 휴대폰 웹의 로그인 · 2단계 인증은 포털이 맡는다
- **결정(위임 판단, 보안)**: #249 배포 직후 휴대폰 웹(/m/)에서 2단계 인증(TOTP)을 건너뛰는 문제를 찾았다. 휴대폰 웹은 자기 이메일 · 비밀번호 로그인과 세션 유무만 확인했고, 포털 라우터도 MFA 게이트보다 먼저 휴대폰 웹으로 옮겼다. 이 때문에 2단계 인증을 등록한 계정이 비밀번호만으로 할 일 · 업무를 열 수 있었다. 소셜 로그인 사용자는 휴대폰 웹에 로그인할 수 없었다. 이렇게 바꾼다.
  - 휴대폰 웹에는 로그인 화면을 두지 않는다. 포털과 같은 판정(utils/mfaGate)으로 포털의 로그인 · 2단계 인증 · 등록 화면으로 보낸다.
  - 포털은 MFA 게이트를 통과한 뒤에만 휴대폰 웹으로 옮긴다.
  - 계정 설정은 휴대폰에서도 포털에 둔다. 등록 화면과 휴대폰 웹 사이를 계속 오가지 않게 하기 위해서다.
- **세부**: 네이티브 앱(mobile/ Capacitor)에는 아직 2단계 인증 화면이 없다. 그래서 2단계 인증이 필요한 계정은 로그아웃시키고 웹 포털을 쓰라고 안내한다. 전에는 비밀번호만으로 들어갈 수 있었다.
- **상태**: vue3 #250. VM에서 고치기 전 우회를 재현했다(F-MV-14 실패). 고친 뒤 F-MV-01~14 12개와 단위 31개가 통과했다.

### D-1111-09 휴대폰 기본은 다시 데스크톱 화면, 라이트 버전은 설정에서 · 맨 위 「홈 화면에 추가」 띠
- **결정**: 휴대폰 기본 화면을 PC와 같은 데스크톱 화면으로 되돌린다. 라이트 버전(휴대폰 웹 /m/)은 설정 › 테마 설정 「휴대폰 화면」에서 선택한 휴대폰에서만 사용한다(「기본 모바일 모드는 기존 PC 버전의 스타일을 유지하지만 … 그쪽 설정에 들어가서 했을 때 그렇게 보이고」). D-1111-07 중 「기본을 휴대폰 웹으로」만 변경하고, 휴대폰 웹과 「내 일만」 범위는 유지한다.
- 홈 화면에 앱으로 추가하지 않은 휴대폰에는 화면 맨 위에 작은 띠(「홈 화면에서 앱처럼 열기 · 추가 · 다시 보지 않기」)를 표시한다. 「추가」를 누르면 안드로이드에서는 설치 창을, iPhone에서는 공유 단추 안내를 표시한다. 「다시 보지 않기」는 웹으로 계속 사용하겠다는 뜻이므로 해당 기기에서는 띠를 다시 표시하지 않는다.
- **세부(위임 판단)**:
  - 띠는 위쪽 막대를 가리지 않도록 그 위에 배치하고, 막대를 띠 높이만큼 내린다. 데스크톱 화면에서도 띠의 글자를 휴대폰 글자 크기로 키운다.
  - 휴대폰 웹에도 같은 띠를 표시하고, 「다시 보지 않기」 선택을 두 화면에 공통으로 적용한다.
  - 첫 접속 시 라이트 버전 사용 여부를 묻는 창은 다시 도입하지 않는다. 라이트 버전은 설정에서만 선택한다.
- **상태**: vue3 #251. VM에서 휴대폰 시험 14개와 단위 시험 34개가 통과했다.

### D-1111-10 서버형 에이전트는 공유 파드에서 처리하고, CLI 에이전트만 대화별 파드를 쓴다
- **결정**: 채팅 처리 방식을 두 가지로 나눈다(「서버사이드의 딥 에이전트나 이런 경우는 이전 방식으로 가고 CLI 에이전트의 유형인 클로드 코드와 코덱스는 파드를 만들어야 되고 … 대기 시간에는 그 표시까지 주는 것이 맞습니다」).
  - 서버형(딥 에이전트): 여러 파드가 대화를 나누어 처리한다. 진행 중인 답변이 있는 대화의 재접속 · 중지 · 방향 바꾸기 · 새 질문은 그 답변을 생성하는 파드로 넘긴다(넘겨주기). 9월 이전의 Redis 조정 코드는 되살리지 않는다.
  - CLI형(코덱스, cli-agent의 Claude Code · Codex): 대화별 파드를 유지한다. 라우터는 파드를 만들기 전에 로그인 토큰을 확인한다. 파드가 준비되는 동안에는 화면에 「에이전트를 준비하고 있어요 · N초」를 표시한다.
  - cli-agent(Claude Code · Codex) 채팅도 이번에 CLI형 방식으로 연결한다.
- **배경**: 9월 17일에는 모든 에이전트의 채팅을 대화별 파드로 옮겼다. CLI 에이전트의 세션을 분리하려면 파드를 나눠야 했기 때문이다(이 결정은 이미 논의를 마쳤다). 그러나 서버형인 딥 에이전트도 새 대화나 30분 동안 쓰지 않은 대화마다 파드가 시작될 때까지 16~40초를 기다려야 했고, 그동안 화면에는 아무것도 표시되지 않았다(「/m 버전과 /라이트 버전 둘 다 대화의 기본 AI한테 질문했을 때 반응이 없는 문제가 있네」). 로그인하지 않은 요청으로도 파드를 띄울 수 있었다. 랭체인 공식 설계 역시 서버 한 대가 여러 대화를 처리하며, 대화를 특정 서버에 고정하는 방식은 권장하지 않는다.
- **세부(위임 판단)**:
  - 넘겨주기는 SDK(process-gpt-agent-sdk 0.12.0)에 둔다. Redis에는 「이 대화는 이 파드가 처리 중」이라는 한 줄만 기록한다. 이벤트와 지시 문장은 Redis를 거치지 않으므로 이후 추가된 방향 바꾸기(9/30)도 따로 손볼 필요가 없다.

  - cli-agent 채팅은 CLI를 반드시 지정해야 한다(Claude Code 또는 Codex). 지정하지 않으면 기본 CLI로 대신 실행하지 않고 오류로 알린다.
