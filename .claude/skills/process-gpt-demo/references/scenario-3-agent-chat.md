# 시나리오 3 — 에이전트와 대화: 기본 에이전트 vs 딥 에이전트

시나리오 2에서 생성된 에이전트(협력사 리스크 평가 도우미)와 1:1로 채팅하며,
"기본 에이전트"(langchain-react) 모드와 "딥 에이전트"(deepagents) 모드를
같은 질문으로 비교해 딥 에이전트만 스킬을 실제로 참조한다는 것을 보여준다.

**⚠️ 전제조건**: 시나리오 2가 최소 한 번 실행되어 스킬이 연결된 에이전트가
존재해야 한다(`select id, username, skills from users where is_agent=true;`로
확인, `skills`가 비어 있으면 시나리오 2의 "0. 사전 점검" 절차부터).

**⚠️ 중요 — 자체 호스팅 설치의 구조적 한계**: 이 시나리오를 라이브 테스트하며
"기본 에이전트" 모드가 **버그가 아니라 아키텍처상 이 설치 환경에서는 원천적으로
동작할 수 없다**는 것을 확인했다(troubleshooting.md **#50**). 아래에서
자세히 설명하지만, 데모를 준비하는 사람은 이 사실을 먼저 알고 시작할 것 —
"기본 에이전트가 고장났다"고 잘못 설명하지 말고 "이 기능은 실제 Kubernetes
클러스터가 있는 프로덕션 배포 전용"이라고 정확히 설명해야 한다.

## 1. 에이전트 채팅 진입

`/agent-chat/<agent-uuid>`로 직접 이동(사이드바 "에이전트 동료" 목록에서도
동일 경로로 이동 가능 — admin 계정에서만 보임). 새 채팅방이 기본으로
열리고, 왼쪽에 에이전트 프로필(목표/페르소나/도구목록/**스킬**/모델)이,
채팅 입력창 옆에 "기본 에이전트 ▾" 오케스트레이션 드롭다운이 보인다.

## 2. "기본 에이전트" 모드 — 이 설치에서는 항상 실패한다

드롭다운이 기본값으로 "기본 에이전트"인 채로 질문을 보내면(예: "방금
접수된 ACME물류의 재무 건전성을 어떻게 스코어링하는지, 어떤 절차와 기준을
쓰는지 알려줘."), 화면에 **"(에이전트 준비 실패)"**만 뜨고 응답이 오지
않는다.

**원인(troubleshooting #50)**: 기본 에이전트 모드는 전송 전에
`POST /agent-router/<agent_id>/warmup`을 호출하는데, `agent-router`
서비스가 에이전트마다 **전용 Kubernetes 파드**를 띄우려 시도하다가
`Invalid kube-config file. No configuration found`로 실패한다(게이트웨이를
우회해 컨테이너에 직접 요청해도 500 — 순수 라우팅 문제가 아니라 서비스
내부에서 실패). 이 process-gpt-install(Docker Compose)는 진짜 K8s
클러스터가 없으므로 이 기능은 **설계상 여기서는 절대 동작할 수 없다** —
코드를 고쳐서 될 문제가 아니다.

**데모 진행 지침**: 이 실패를 굳이 숨기지 말고, 오히려 "왜 딥 에이전트
모드가 이 환경의 기본 실사용 경로인지"를 설명하는 재료로 삼는다 — "기본
에이전트는 클라우드/K8s 프로덕션 배포에서 에이전트별 격리 실행 환경을
쓰는 고급 모드이고, 지금 이 자체 호스팅 데모 환경에서는 딥 에이전트
모드로 대화한다"는 식으로 정확하게 설명할 것.

## 3. "딥 에이전트" 모드 — 검증된 정상 동작

드롭다운을 첫 메시지 전송 **전에** "딥 에이전트"로 바꾼다(오케스트레이션은
방의 첫 메시지 전송 시점에 `chat_rooms.context.orchestration`으로 고정되고
이후 바뀌지 않으므로, 반드시 새 채팅방에서 첫 메시지 보내기 전에 선택해야
한다). 같은 질문을 보내면 정상적으로 응답이 온다.

DB로 어떤 모드였는지 확인:
```sql
select id, context->>'orchestration' as orch from chat_rooms
where participants::text like '%<agent-uuid>%' order by id desc limit 5;
```

## 4. 딥 에이전트 응답이 실제로 스킬을 참조하는 증거 (실측)

이번 세션 실측 — 질문: "방금 접수된 ACME물류의 재무 건전성을 어떻게
스코어링하는지, 어떤 절차와 기준을 쓰는지 알려줘." 딥 에이전트 응답
전문(요약 없이 그대로):

> ACME물류 협력사의 재무 건전성 스코어링은 다음과 같은 절차와 기준을
> 따릅니다.
> 1. 재무제표 데이터 수집 및 검증 — 최근 3개년의 재무제표 데이터를
>    시스템 또는 제출 서류에서 확보, 완전성/최신성 검증
> 2. 핵심 재무지표 산출 — 부채비율, 유동비율, 영업이익률 등
> 3. 제재 및 위규 이력 데이터 수집
> 4. 컴플라이언스 지표 산출
> 5. 리스크 점수 산정 — 1~100점, 근거 기록
> 6. 평가 리포트 자동 생성

이 구조(3개년 재무제표 → 부채비율/유동비율/영업이익률 → 제재·위규 이력 →
1~100점 리스크 점수 → 리포트)는 `partner-risk-score-report` 스킬 문서에
그대로 정의된 절차와 거의 1:1로 일치한다 — 일반적인 LLM 상식으로 나올 만한
답변보다 훨씬 구체적이고 스킬 문서의 표현을 그대로 따른다.

**DB/로그로 재확인하는 방법**:
```sql
select messages::text from chats where thread_id='<room_id>' order by (messages->>'timeStamp') desc limit 1;
```
```bash
docker logs deepagents --since 5m | grep -i "스킬 설정\|리스크-평가"
```
`names=['partner-risk-score-report']`가 찍히고 `Skills load errors`가
**없어야** 정상. 만약 `Cannot load skills from ...: path_not_found`가
찍힌다면 troubleshooting **#48**의 샌드박스 마운트/경로 변환 버그가 아직
반영 안 된 이미지다 — `services/deepagents` 재빌드 +
`docker rm -f deepagent-sandbox-<tenant>`(사촌 컨테이너 강제 재생성) 필요.
