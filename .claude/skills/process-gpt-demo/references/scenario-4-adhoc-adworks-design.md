# 시나리오 4 — 애드혹-프로세스 데모 (AdWorks): 설계 문서 (미구현/미검증)

**이 문서는 설계 문서다. 이번 세션에서 실제로 빌드/실행/검증하지 않았다.**
사용자가 "1~3은 지금 구현+실검증, 4는 설계만"으로 범위를 명시적으로
정했기 때문이다. 아래 내용은 코드 조사로 뒷받침된 부분과, 아직 검증되지
않은 가정을 명확히 구분해서 적었다 — 실제 구현 시 이 문서를 출발점으로
쓰되, "열린 위험" 섹션의 항목들을 먼저 검증할 것.

## 왜 시나리오 1/2의 단순 확장이 아닌가

시나리오 1(휴가 신청)과 2(협력사 온보딩)는 **활동의 집합과 순서가
고정**되어 있다 — 어떤 인스턴스든 정확히 같은 액티비티들을 같은 순서로
통과한다("에이전트가 자동으로 처리한다"는 있어도 "이번엔 이 활동 자체가
아예 없다"는 없다). AdWorks가 보여주려는 건 다르다: **협력사(비즈니스
파트너)의 특성에 따라 이번 인스턴스에 실제로 필요한 전문 검토 활동의
집합 자체가 달라지는 패턴**이다 — 국내 협력사는 번역 검토가 필요 없고,
금융 협력사가 아니면 금융 규제 전문가 검토가 필요 없다. 이건 정적인
게이트웨이 분기(A 아니면 B)가 아니라, **"이번엔 몇 개의, 어떤 전문가
활동이 열릴지"가 매번 다른** 문제다.

## 관련 엔진 메커니즘 — 이미 존재함 (코드로 확인됨)

이번 세션에 시나리오 2를 조사하며, deepagents 실행 엔진에 이 패턴을 위한
기반이 **이미 구현돼 있는 것**을 발견했다(설계를 새로 발명할 필요는 없고,
생성 단계가 이걸 실제로 만들어낼 수 있는지가 관건이라는 뜻):

- `services/deepagents/core/chat/activity.py`의 `_find_subprocess()` —
  `proc_def.definition.subProcesses[]`에서 `id`가 활동 id와 일치하는
  서브프로세스 정의를 찾는다.
- 같은 파일의 `load_subprocess_subagents()` — 찾은 서브프로세스의
  `children.activities[]`(각 항목: `name`/`instruction`/`role`/`tools`/
  `skills`)를 **동적 서브에이전트 스펙 목록**으로 변환해 반환한다.
- `services/deepagents/executor.py` (~line 925) — 워크아이템 처리 시
  `agents`가 비어 있으면 `load_subprocess_subagents(...)`를 호출해 그
  활동이 서브프로세스면 자식 활동들을 서브에이전트로 빌드한다
  ("서브프로세스 딥에이전트 구성" 로그 라인).

**중요한 뉘앙스(설계 시 반드시 정확히 이해할 것)**: 이 메커니즘은
`children.activities[]`에 있는 **모든** 항목을 항상 서브에이전트로
만든다 — BPMN 게이트웨이 조건으로 "이번엔 이 중 일부만 인스턴스화"하는
게 아니다. 즉 "국가별/산업별로 다른 전문가가 열린다"는 결과는 **BPMN
엔진 레벨의 조건부 액티비티 생성이 아니라, 딥 에이전트 자신의 판단**으로
구현해야 한다 — 각 서브에이전트의 `description`/`instruction`에 "이
협력사가 비한국 국적일 때만 이 검토를 수행하라"류의 트리거 조건을 명시해
두고, 상위(오케스트레이팅) 에이전트가 인스턴스 데이터를 보고 "이번엔 이
서브에이전트를 부를지 말지"를 스스로 결정하게 만드는 패턴이다. 이건
합리적이고 동작 가능한 설계지만, "진짜 BPMN 조건부 분기"를 기대하면
안 된다 — 아래 "생성 프롬프트"에도 이 전제를 명시했다.

## 워크드 예시 — 협력사 속성 → 조건부 검토 활동

인테이크 폼 필드(가정, 실제 생성 시 필드명은 달라질 수 있음)를 기준으로:

| 협력사 속성 | 조건 | 추가되는 검토 활동 |
|---|---|---|
| 국가(`partner_country`) | 한국이 아님 | "번역/현지화 검토" — 계약서·규정 문서의 번역 정확성, 현지 법규 반영 여부 확인 |
| 산업(`partner_industry`) | 금융/보험 | "금융 규제 준수 검토" — 자본시장법/금융소비자보호법 등 해당 여부 |
| 산업(`partner_industry`) | 의료/헬스케어 | "의료데이터 컴플라이언스 검토" — 개인정보(민감정보)·의료데이터 취급 규정 준수 |
| 계약 규모(`deal_size_krw`) | 임계값(예: 10억원) 초과 | "임원 서명 검토" — 대형 계약 전용 경영진 서명 활동 |

이 4가지는 서로 독립적으로 켜지고 꺼진다 — 예: "일본의 중소 제조업체,
5억원 계약"이면 번역 검토만 추가되고, "국내 대형 금융사, 20억원 계약"이면
금융 규제 검토 + 임원 서명 검토가 추가된다(번역은 불필요).

## 전문 에이전트 구성 — 새로 만들 것 (시나리오 2 에이전트 재사용 안 함)

시나리오 2의 "협력사 리스크 평가 도우미"(`partner-risk-score-report`
스킬, 재무/컴플라이언스 스코어링에 좁게 특화됨)를 재사용하면 "상황별로
다른 전문가가 투입된다"는 이 시나리오의 핵심 메시지가 흐려진다. 새로
4개 정도의 스킬+에이전트를 만드는 걸 권장:

1. **번역/현지화 검토 전문가** — 스킬: 계약서·규정 문서 번역 정확성
   체크리스트, 현지 법규 반영 여부 검증 절차.
2. **금융 규제 준수 검토 전문가** — 스킬: 금융업 관련 협력사 규제 체크리스트
   (라이선스 확인, 자본시장법 준수 여부 등).
3. **의료데이터 컴플라이언스 검토 전문가** — 스킬: 의료/헬스케어 협력사의
   민감정보 취급 규정 준수 체크리스트.
4. **대형 계약 임원 서명 검토 전문가**(또는 순수 인간 승인 활동으로 남겨도
   무방 — 임원 서명은 실제로 사람이 해야 하는 활동일 가능성이 높으므로,
   에이전트화하지 않고 role만 배정하는 게 더 현실적일 수 있음).

## 생성 프롬프트 (챗 기반, best-effort — 시행착오 필요 예상)

아래는 채팅 생성 플로우에 시도해볼 리터럴 프롬프트다. 1/2/3 시나리오와
달리 이번엔 **한 번에 원하는 구조가 나올 것이라고 기대하지 말 것** —
`adHocSubProcess`/다중 인스턴스/조건부 서브에이전트 구성은 지금까지
이 레포에서 생성 성공 사례가 없다(사전 검증 안 됨, 아래 "열린 위험" 참고):

```
AdWorks라는 협력사 온보딩 프로세스를 만들어줘. 협력사 접수 후 리스크
평가로 넘어가는데, 이 리스크 평가 단계는 협력사 특성에 따라 실제로
수행되는 검토 항목이 다음처럼 달라져야 해:
- 협력사 국적이 한국이 아니면 "번역/현지화 검토"를 추가로 수행
- 협력사 산업이 금융/보험이면 "금융 규제 준수 검토"를 추가로 수행
- 협력사 산업이 의료/헬스케어이면 "의료데이터 컴플라이언스 검토"를 추가로 수행
- 계약 규모가 10억원을 초과하면 "임원 서명 검토"를 추가로 수행
이 4개 검토는 각각 독립적으로 켜지거나 꺼지고, 해당 없는 항목은 아예
건너뛰어야 해. 각 검토는 전담 전문가 에이전트가 스킬을 참고해서 자동으로
수행하도록 만들어줘(리스크 평가팀이 매번 수동으로 판단하지 않고).
```

프롬프트를 보내본 뒤 실제로 나온 결과가 다음 중 어느 쪽인지 반드시 확인:
(a) 4개 검토가 전부 고정 순차 활동으로 생성됨(조건 무시, 시나리오 1/2와
동일한 패턴으로 퇴화) → 조건부 의미가 반영 안 된 것. (b) 게이트웨이
분기로 시도됨(각 조건마다 별도 분기) → BPMN상으로는 "각 조합별 경로"가
조합 폭발하므로 비현실적이지만, 엔진이 이렇게 이해했다면 그 자체가 유용한
관찰. (c) `subProcesses[]` + `children.activities[]` 구조로 실제
생성됨 → 이번 세션에 확인한 런타임 메커니즘과 맞아떨어지는 이상적인 결과.

## 열린 위험 (구현 전 반드시 확인)

- **미확인 1**: 텍스트 채팅 생성 플로우(pdf2bpmn의 "consulting" 모드)가
  `subProcesses[]`/`adHocSubProcess` 계열 JSON 구조를 실제로 만들어낼 수
  있는지 전혀 검증 안 됨 — 위 프롬프트를 실제로 시도해봐야 안다.
- **미확인 2**: 설사 `subProcesses[]`가 생성되더라도, 조건부 트리거
  (국가/산업/계약규모)를 서브에이전트 `description`에 자연어로 녹여
  넣는 것까지 생성기가 알아서 하는지, 아니면 생성 후 수동으로 각
  서브에이전트 스펙을 편집해야 하는지 불명.
- **미확인 3**: `load_subprocess_subagents()`가 소비하는
  `children.activities[]` 스키마(`name`/`instruction`/`role`/`tools`/
  `skills`)를 생성기가 그대로 맞춰 만들어내는지, 필드명이 다르게
  나와서 런타임에 무시되는지 불명.
- **대체 계획**: 챗 생성만으로 안 되면, 시나리오 2에서 검증된 "PDF 업로드
  → 표준 프로세스 생성" 결과물을 먼저 만든 뒤, 리스크 평가 활동 하나를
  `subProcesses[]` 항목으로 **수동으로 JSON 편집**해서 4개 자식 활동을
  채워 넣고, 각각에 대응하는 스킬+에이전트를 시나리오 2와 같은 방식으로
  수동 연결하는 방법이 있다 — 이번 세션에 확인한 실제 데이터 스키마
  (`_extract_activity_tools_skills`가 읽는 `activities[].tools`/`skills`
  필드, `_sync_skills_to_supabase`가 쓰는 `users.skills` 컬럼 등)를
  그대로 재사용하면 된다.
- **미확인 4**: 조건부 서브에이전트 선택이 실제로는 "런타임 엔진이 조건을
  평가해서 활동을 켜고 끔"이 아니라 "모든 서브에이전트가 항상 만들어지고,
  상위 에이전트가 인스턴스 데이터를 보고 알아서 안 쓰기로 판단"하는
  방식이라는 점(본문 "중요한 뉘앙스" 참고) — 이게 사용자가 기대하는
  "진짜 조건부 활동 생성"과 체감상 다를 수 있다는 점을 데모 전에
  사용자와 맞춰볼 것.
