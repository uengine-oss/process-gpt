# 03 – Elicit Artifacts: 스킬/에이전트/DMN 후보 제시 + 선택 (HITL)

**목적**: 1단계에서 만든 프로세스 정의 JSON 을 분석해 **재사용 스킬 · 에이전트 · DMN 의사결정 후보**를 뽑고, 사용자에게 *무엇을 만들지* 한 번에 묻는다. 사용자가 고른 것만 실제로 만든다. 이것이 이 skill 의 핵심 **HITL(Human-In-The-Loop)** 단계다.

> pdf2bpmn 의 "통합 elicit" 흐름을 옮긴 것입니다. 스킬/에이전트/DMN 후보를 **한 번**에 함께 묻되, **반드시 `AskUserQuestion`** 으로 묻습니다(아래 "사용자에게 묻기").

산출물: 선택 결과를 받아 선택분만 스킬(가능하면 skill-creator 로 생성)/에이전트/DMN 으로 만들고 `.bpmn/process-definition.json` 에 반영한다.

---

## 핵심 원칙

0. **🔴 반드시 "구체 후보를 담은 선택 질문"이어야 한다 (빈 질문/빈 후보 금지).**
   - 질문 **전에** 먼저 프로세스 elements 에서 종류별(스킬/에이전트/DMN) **구체 후보 3개 내외를 도출**한다(아래 "후보 도출 규칙"). 이 도출을 건너뛰고 질문부터 내보내면 안 된다.
   - **반드시 `AskUserQuestion` 도구로** 묻는다(프로즈로 끝내지 말 것 — 09 "단일 세션 실행"). `AskUserQuestion` 은 한 번의 호출에 **최대 4개의 질문**을 담을 수 있고, 각 질문은 **최대 4개의 구조화된 옵션**(`label`+`description`)과 `multiSelect` 를 지원한다. 이 구조를 그대로 활용한다 — 종류(스킬/에이전트/DMN)마다 **별도 질문 1개**를 만들고, 그 질문의 `options` 에 후보들을 넣는다(`multiSelect: true`). **후보 없는 빈 질문은 명백한 위반**이므로, 후보가 있는 종류만 질문에 포함한다.
     ```
     AskUserQuestion(questions=[
       {
         "question": "이 프로세스에 추가할 스킬을 골라주세요 (안 고르면 건너뜁니다)",
         "header": "스킬",
         "multiSelect": true,
         "options": [
           {"label": "휴가 잔여일수 검증", "description": "신청 전 잔여 연차 확인 (활동 2개)"},
           {"label": "결재 검토 처리", "description": "신청서 기준 검토·승인 (활동 1개)"},
           {"label": "결과 통보 발송", "description": "승인/반려 결과 통보 (활동 2개)"}
         ]
       },
       {
         "question": "이 프로세스에 배치할 에이전트를 골라주세요 (안 고르면 건너뜁니다)",
         "header": "에이전트",
         "multiSelect": true,
         "options": [
           {"label": "팀장 — 휴가 검토", "description": "검토·승인 담당"},
           {"label": "인사팀 — 휴가 등록", "description": "승인 휴가 반영"}
         ]
       },
       {
         "question": "이 프로세스에 추가할 DMN 규칙을 골라주세요 (안 고르면 건너뜁니다)",
         "header": "DMN",
         "multiSelect": true,
         "options": [
           {"label": "승인 여부 판단", "description": "승인→등록 / 반려→통보"}
         ]
       }
     ])
     ```
   - 종류가 3개보다 적으면(예: DMN 후보가 없으면) 그 종류의 질문은 아예 빼고, 있는 종류만 질문 배열에 담는다. 옵션이 4개를 넘는 종류는 가장 재사용 가치가 높은 상위 4개만 추린다(아래 "후보 도출 규칙"의 3개 내외 목표와 일치).
   - 금지 예: "어떤 스킬/에이전트/DMN 을 추가할까요?"(옵션 없음)·"…만들까요?"(예/아니오만 있는 생성여부 질문) — 절대 금지. 모호어 '자동화 요소' 같은 표현도 쓰지 않고 **스킬·에이전트·DMN** 을 그대로 쓴다.
   - 정말 도출되는 후보가 0개인 극히 예외적 경우에만, 질문 대신 "추가할 스킬·에이전트·DMN 이 없어 보입니다. 바로 폼·참조정보로 진행할게요" 라고 안내하고 다음 단계로 넘어간다(빈 질문 금지).
1. **묻지 않고 다 만들지 않는다.** 후보를 보여주고 선택을 받는다. 아무것도 안 고르면 그 종류는 건너뛴다. 강요 금지.
2. **한 번에 묻는다.** 스킬·에이전트·DMN 을 따로 여러 번 묻지 말고, 한 번의 `AskUserQuestion` 호출에 세 질문(있는 종류만)을 함께 담는다.
3. **후보는 JSON 에서 도출한다.** 지어내지 말 것. 아래 도출 규칙대로 실제 elements 를 근거로 후보를 만든다.
4. **선택 후 즉시 반영.** 사용자가 고르면 스킬/에이전트/DMN 을 선택된 것만 생성하고 `process-definition.json` 을 업데이트한다.

## 후보 도출 규칙

> **추천 개수 목표**: 각 종류(스킬/에이전트/DMN)마다 **3개 내외의 후보를 적극적으로 추천**하는 것을 목표로 한다(가능하면 3개, `AskUserQuestion` 옵션 상한은 종류당 4개). 작은 선형 프로세스라도 재사용·자동화·판단 자동화 관점에서 의미 있는 후보를 발굴해 채운다. 후보가 정말 1~2개뿐이면 그대로 두고, 전혀 없으면 그 종류의 질문 자체를 만들지 않는다. 후보는 반드시 실제 elements 에 근거해야 하며, 지어내거나 프로세스와 무관한 것을 넣지 않는다.

### 스킬 후보 (→ [04-skills.md](04-skills.md))
재사용 가능한 "공통 작업"을 찾는다. 근거:
- 여러 Activity 의 `instruction`/`description` 이 **유사한 의도**로 반복되면(예: "기준 대조 검토", "서류 확인") 그 묶음을 스킬 후보 1개로.
- 단일 Activity 라도 그 자체로 **독립적·재사용성 높은 절차**(예: "정책 기준 일치성 검증")면 후보가 될 수 있다.
- 후보 1개 = `{ id(safe_name kebab-case), label(한글 스킬명), description(1줄), source_activity_ids(근거 액티비티) }`.
- 후보가 없으면(작은 선형 프로세스) 스킬 질문 자체를 만들지 않는다.

### 에이전트 후보 (→ [05-agents.md](05-agents.md))
"역할 + 그 역할이 반복 수행하는 스킬" 조합을 에이전트 후보로.
- 근거: `roles` 와, 각 역할이 담당하는 Activity 묶음. 스킬 후보가 있으면 (역할 × 스킬) 로 매칭.
- 후보 1개 = `{ candidate_id("agent_<역할>_<스킬>"), label("역할명 — 스킬명"), description("담당 활동 N개 · 역할/목표 요약"), role_name, activity_ids }`.
- 조직도 등 기존 에이전트 정보가 있으면 "기존 재사용" 으로 표시(신규 생성 안 함). 이 skill 의 일반적 상황(조직도 없음)에서는 전부 신규 후보.

### DMN 후보 (→ [06-dmn.md](06-dmn.md))

분기를 전부 DMN 후보로 올리지 않는다. **모든 분기는 기본적으로 `Sequence.condition`(BPMN 조건식)만으로 표현**하고, 그중 **의사결정 테이블로 분리할 재사용 가치가 있는 것만** DMN 후보로 승격한다.

**필요조건 (구조 — 아래 두 가지를 모두 만족해야 후보 자체가 성립)**:
- `type` 이 **ExclusiveGateway** 이다 (Parallel/Inclusive 는 제외 — 조건 평가 의미가 다름).
- outgoing Sequence 가 **2개 이상**이다.

**승격조건 (재사용 가치 — 아래 세 가지 중 하나 이상을 만족해야 실제 후보로 제시)**:
1. **로직 반복**: 같은 이름·유사 의도의 게이트웨이가 이 프로세스 안에 2곳 이상 등장하거나, 다른 프로세스/활동에서도 그대로 재사용될 만한 범용 판단이다 (예: "리스크 등급 판정", "결재 한도 판단", "휴가 승인 가능 여부" 처럼 이 프로세스 밖에서도 같은 로직을 다시 쓸 법한 경우).
2. **규칙 복잡도**: 분기 조건이 **3개 이상**이거나, 분기 조건 하나를 판단하는 데 **여러 입력 필드를 조합**해야 한다(단일 값 비교가 아니라 AND/OR 등 복합 조건).
3. **정책성·가변성**: 조직 정책·규정·기준액처럼 **코드 재배포 없이 운영자가 자주 바꿔야 하는 값/기준**이다 (예: "승인 한도 금액", "리스크 점수 임계치", "휴가 사용 규정 상한"). 프로세스 흐름 구조 자체와 무관하게 값만 튜닝될 수 있어야 한다.

**제외(=DMN 후보로 만들지 않음)**: 단일 조건의 단순 2지 분기(예: 흔한 "승인/반려" 예·아니오 판단 1개)이면서 위 세 가지 중 어느 것도 해당하지 않는, 이 흐름 안에서만 쓰이는 1회성 분기. 이런 분기는 `Sequence.condition`만으로 충분히 표현되므로 DMN 으로 분리할 가치가 없다.

- 같은 이름의 게이트웨이가 여러 개면 **하나의 후보로 병합**.
- 후보 1개 = `{ candidate_id("dmn::<gateway_id>"), label("[프로세스명] 게이트웨이명"), description("분기 N개: 조건1 → 대상1 / 조건2 → 대상2 · 재사용 근거: <위 1~3 중 해당 사유 한 줄>"), gateway_ids }`. **description 끝에 반드시 재사용 근거를 한 줄 붙인다** — 사용자가 왜 이 분기가 DMN 후보로 뽑혔는지 바로 알 수 있어야 한다.

## 사용자에게 묻기 — `AskUserQuestion` (필수)

**반드시 `AskUserQuestion` 도구**로 묻는다(프로즈로 끝내거나 확인 없이 다음 단계로 넘어가지 말 것). 위 "핵심 원칙 0" 의 예시처럼, 종류(스킬/에이전트/DMN)마다 **하나의 질문**을 만들고 그 질문의 `options` 에 후보를 담는다. `header` 는 "스킬"/"에이전트"/"DMN" 으로, `multiSelect` 는 항상 `true`.

- **반드시 구체 후보를 옵션으로 나열**한다. "어떤 스킬/에이전트/DMN 을 추가할까요?"(옵션 없음)·"스킬/에이전트/DMN 을 만들까요?"(생성 여부만 묻는 질문) 같은 **빈 질문은 절대 금지** — 고를 옵션이 없으면 위반이다.
- 후보가 없는 종류는 질문 자체를 빼고, 모든 종류가 0개인 극히 예외적 경우에만 `AskUserQuestion` 대신 "추가할 스킬·에이전트·DMN 이 없어 보입니다. 바로 폼·참조정보로 진행할게요" 라고 안내하고 다음 단계로 넘어간다.
- 옵션 목록 외의 커스텀 요청(이름 변경, 새 스킬/규칙 추가 등)은 각 질문에 자동 제공되는 "Other" 자유 입력으로 받아 반영한다.
- 각 종류 후보(옵션)는 **3개 내외**가 이상적이고 **최대 4개**(도구 상한)까지다. DMN 처럼 게이트웨이 수만큼만 나오면 1~2개여도 억지로 늘리지 않는다.
- `option.description` 에 후보 설명을 담아, 사용자가 라벨만 보고도 무엇을 만드는지 알 수 있게 한다(예: "신청 전 잔여 연차 확인 (활동 2개)").
- 질문의 `question` 텍스트 첫머리에 "스킬=반복 작업을 한 번 정의해 재사용", "에이전트=특정 역할을 자동으로 처리하는 담당", "DMN=갈림길 판단 규칙을 표로 정리" 처럼 용어를 풀어 설명해도 좋다.

## 선택 결과 처리

사용자 응답을 받은 뒤:

1. **스킬을 골랐으면** → [04-skills.md](04-skills.md) 로드 → 선택된 스킬만 생성(가능하면 skill-creator, 없으면 직접 작성) + JSON 반영.
2. **에이전트를 골랐으면** → [05-agents.md](05-agents.md) 로드 → 선택된 역할·스킬에 에이전트 연결 + JSON 반영.
3. **DMN 을 골랐으면** → [06-dmn.md](06-dmn.md) 로드 → 선택된 게이트웨이를 DMN 의사결정/규칙으로 생성 + JSON 반영.
4. 아무것도 안 골랐으면 → 바로 다음 단계(폼)로 진행한다.

> 의존성: 에이전트 후보는 스킬과 엮일 수 있으므로, 스킬 → 에이전트 → DMN 순으로 처리하는 것이 자연스럽다. 단 세 가지는 독립이므로 사용자가 고른 것만 해당 단계로 가면 된다.

## 멀티 프로세스일 때 — 프로세스마다 별도 호출로 묻는다

여러 프로세스를 만드는 중([11-multi-process.md](11-multi-process.md))이면, 멀티 프로세스는 **항상 일괄 고정 절차**(11단계 §4)로 진행하며 이 선택 단계는 그 **아티팩트 일괄 질문**에 해당한다. JSON 일괄 생성이 끝난 뒤, **각 프로세스마다 그 프로세스의 후보로 별도 `AskUserQuestion` 호출**을 연달아 실행해 묻는다. 후보는 그 프로세스의 elements 에서 도출되므로 프로세스마다 다르며, **앞 프로세스의 선택을 자동 적용하거나 묻지 않고 자동 수락하지 않는다**(HITL 유지).

- 각 호출의 `question` 앞머리에 **"[k/N: <프로세스명>]"** 라벨을 붙여 어느 프로세스 질문인지 분명히 한다.
- 한 프로세스당 이 호출은 1회뿐(질문은 최대 3개: 스킬/에이전트/DMN). **모든 프로세스의 응답을 다 받은 뒤** 후속 단계를 일괄 실행한다.
- **프로세스 간 재사용**: 사용자가 고른 결과가 앞 프로세스에서 이미 만든 것과 동일 의도면 중복 생성하지 말고 기존 id 를 연결한다(11단계 §5). 이는 자동 적용이 아니라 중복 제거다.

## 다음 단계 연결 (중요: 폼·참조정보는 자동 진행)

이 선택 단계는 **이 skill 에서 사용자에게 묻는 마지막 단계다.** 폼과 참조정보는 어떤 프로세스든 **항상 생성·연결해야 하는 필수 산출물**이므로, 여기서 *"폼을 만들까요?"* 같은 추가 질문을 **하지 않는다.**

사용자의 스킬/에이전트/DMN 선택을 반영한 뒤에는, **추가 확인 없이 곧바로** 아래를 **연속 자동 실행**한다:

1. 선택된 스킬/에이전트/DMN 생성 + JSON 반영 (위 "선택 결과 처리").
2. [07-forms.md](07-forms.md) 로드 → **모든 UserActivity 폼 자동 생성** + JSON 반영. (스킬/에이전트/DMN 을 하나도 안 골랐어도 진행한다.)
3. [08-reference-info.md](08-reference-info.md) 로드 → **inputData/conditionData 자동 연결** + JSON 최종 업데이트.

그런 다음 검증·완료 단계로 이어진다([09-service-execution.md](09-service-execution.md)). 단계 사이에 "다음으로 넘어갈까요?" 를 묻지 않는다.
