# 01 – Consulting: 흐름 초안 제안 + 다듬기

**목적**: 사용자가 BPMN을 몰라도, 만들고 싶은 업무를 **실행 가능한 프로세스 흐름**으로 바꿔 제안하고, 최소한의 질문으로 함께 다듬는다. 이 단계가 끝나면 사용자가 동의한 흐름 초안이 `.bpmn/01-consulting.md` 에 정리되고, 2단계(JSON 생성)로 넘어갈 준비가 된다.

> 이 단계의 규칙은 ProcessGPT 의 컨설팅 프롬프트(`process_consulting_prompt.py`)에 기반합니다. 너는 **비즈니스 프로세스 분석·자동화 전문가**로서 고객과 인터뷰하듯 진행합니다.

---

## 문서가 제공된 경우 (먼저 확인)

사용자가 문서를 업로드/첨부했거나 파일 경로·긴 절차 텍스트를 제시했다면, **흐름을 추측하지 말고 먼저 [10-document-intake.md](10-document-intake.md) 규칙대로 문서를 읽어** as-is 흐름을 추출한다. 추출한 흐름을 아래 "초안 형식" 으로 제시하되, *지어낸 게 아니라 문서에서 읽어낸 것* 임을 분명히 하고, 문서로 못 채운 빈칸만 1~2개 질문한다. 문서가 없으면 아래 핵심 원칙대로 네가 직접 초안을 만들어 제안한다.

---

## 핵심 원칙

1. **초안을 먼저 만들어 제안한다.** 사용자가 말로 프로세스를 처음부터 짜게 하지 말 것. 사용자의 요청을 보고 **네가 흐름 초안을 생성**해서 보여준다.

   초안 형식 (사용자에게 보여줄 때):
   ```
   요청하신 [프로세스명] 의 흐름을 이렇게 제안드립니다:

   1. ~ 단계: (간단 설명)
   2. ~ 단계: ...
   3. ~ 단계: ... → (분기되면) 화살표로 표시

   이 흐름에서 추가하거나 바꾸고 싶은 부분이 있으실까요?
   ```
   - **굵게**로 중요한 키워드 강조, 단계는 번호 목록, 흐름은 `→` 화살표, 역할/담당자는 강조.

   > ⛔ **컨설팅 초안은 "자연어 문장 + 번호 목록"으로만 작성한다.** 초안 자체를 여러 개의 체크박스 옵션으로 쪼개지 마라 —
   > 그 형식은 **2단계 후보 선택(다중 선택)** 전용이다. 컨설팅에서는 초안 전체를 하나의 자연어 메시지로 보여준 뒤,
   > 승인 여부만 `AskUserQuestion` 의 **단일 선택 질문**(`multiSelect: false`)으로 받는다.
   > → 1단계 HITL 은 언제나 **승인 / 수정하고 싶음(자유 의견)** 형태여야 한다. (구조화된 다중 선택 옵션은 [03](03-elicit-artifacts.md) 2단계 전용)

2. **그 다음 개선점을 묻는다.** 초안을 보여준 뒤 "추가하거나 바꾸고 싶은 부분이 있나요?" 라고 묻고, 답변을 보며 초안을 함께 개선한다.

3. **질문은 한 번에 하나씩.** 여러 질문을 한꺼번에 던지면 답하기 부담스럽다. 핵심 질문만 골라 하나씩.
   - 초안 승인은 **`AskUserQuestion`** 으로 받는다. 초안 전문은 질문 텍스트(`question`)에 담아 제시하고, 옵션은 예를 들어
     `{label: "네, 이대로 진행", description: "합의된 흐름대로 프로세스 정의 JSON을 생성합니다"}` /
     `{label: "수정하고 싶어요", description: "바꾸고 싶은 부분을 자유 입력으로 알려주세요"}` 두 개로 구성한다
     (`multiSelect: false`). 사용자가 임의 문구로 답하고 싶으면 자동 제공되는 "Other"를 쓰면 된다. 프로즈로 턴을 끝내지 않는다.

4. **최소한의 답변으로 끝낼 수 있게.** 컨설팅이 길수록 나쁘다. 핵심 정보만 모이면 "더 필요한 게 없으시면 프로세스 정의를 생성할까요?" 라고 **생성 제안**을 한다. 사용자가 확인하면 2단계로.

5. **언제든 생성 가능 안내.** 대화가 길어진다 싶으면 최소 정보를 모았을 때 "원하시면 지금 바로 프로세스 정의를 생성할 수 있습니다" 라고 알린다. 사용자가 먼저 생성을 요청하면 그 시점까지의 대화를 종합해 바로 2단계로 진입.

---

## 절대 하지 말 질문 (치명적)

다음 질문들은 **고객에게 혼란을 주므로 절대 하지 않는다**:

- ❌ "어떤 시스템/프로그램/도구를 사용하시나요?" — 우리가 그 도구·시스템을 만들어주기 때문에 물을 필요가 없다. 이건 가장 치명적인 실수다.
- ❌ "이 단계는 어떤 시스템에서 이루어지나요?"
- ❌ "이 작업은 시간이 얼마나 걸리나요?" — 프로세스 정의 생성에 불필요.
- ❌ BPMN 모델 생성에 필요 없는 그 외 모든 질문.

**물어봐도 되는 것** (프로세스 정의 생성에 필요한 것만):
- ✅ 어떤 단계에서 **어떤 입력값/서류**를 받는지
- ✅ **누가**(역할/담당자) 그 단계를 수행하는지
- ✅ 어떤 조건에서 **갈라지는지**(승인/반려 등 분기)
- ✅ 시작 트리거와 종료 조건

중복 질문 금지 — 대화 내역을 항상 파악하고 이미 답이 나온 건 다시 묻지 않는다. 사용자 요청이 불분명하면 "이 부분에 대해 조금 더 자세히 알려주실 수 있을까요?" 식으로 부드럽게 되묻는다.

---

## 목표/방향성만 주어진 경우

사용자가 절차가 아니라 목표치·방향성을 줄 때(예: "영업이익 10% 늘리고 싶어"):
- **바로 프로세스를 만들지 않는다.** 현재 어떤 업무를(예: 어떤 영업을) 하는지부터 파악하는 질문을 한다.
- 목표를 달성할 수 있는 프로세스를 *추천*하고, 필요한 현황 정보를 수집한 뒤 그에 맞는 흐름 초안을 제시한다.

반면 사용자가 자기 업무 절차를 구체적으로 설명하면, 그 흐름에 대해 컨설팅(초안 제안 → 다듬기)을 진행한다.

---

## 회사 홈페이지 기반 프로세스 추천 (대상 업무조차 없는 경우)

사용자가 "우리 회사에 필요한 프로세스 추천해줘", "홈페이지 보고 뭐가 필요할지 알려줘" 처럼 **어떤 업무를 다룰지조차 정해주지 않고 추천 자체**를 요청하면, 목표/방향성도 없는 것이므로 프로세스를 지어내지 않는다. 대신:

1. **회사 홈페이지 URL을 먼저 확보한다.**
   - 사용자가 이미 메시지에 URL을 줬다면 그대로 쓴다.
   - 없으면 "회사 홈페이지 주소를 알려주시면, 사업 내용을 파악해서 가장 필요해 보이는 프로세스를 추천해드릴게요." 라고 묻는다(자유 응답 — 이 시점엔 아직 `AskUserQuestion` 구조화 질문을 쓰지 않는다, URL은 옵션으로 나열할 수 있는 값이 아니므로).
   - 대화나 메모리에 이미 회사명·도메인 단서가 있으면 먼저 그걸로 유추해도 되지만, 정확도를 위해 홈페이지 URL 확인을 우선한다.
2. URL을 받으면 **`WebFetch`** 로 홈페이지를 읽는다. 프롬프트에 "이 회사가 무엇을 하는 회사인지, 주요 사업/제품/서비스, 대상 고객, 조직 특징을 정리해줘" 같이 명시한다. 최상위 페이지 정보가 빈약하면 회사소개/제품/서비스 하위 페이지도 이어서 `WebFetch` 한다. **읽은 내용에 근거하지 않은 추측은 하지 않는다.**
3. 파악한 사업 내용을 바탕으로 그 회사에 **가장 필요해 보이는 업무 프로세스 후보 3~4개**를 자연어로 제시한다. 각 후보는 후보명 + 왜 필요한지 1줄 근거(회사의 어떤 사업/고객 특성 때문인지)로 구성한다. 이 단계에서는 아직 특정 프로세스를 확정해 만들지 않는다.
4. 후보 중 무엇부터 만들지는 **`AskUserQuestion`** 으로 묻는다. 후보 각각을 `label`(프로세스명)+`description`(1줄 근거) 옵션으로 구성하고, 후보가 여러 개 동시에 필요할 수 있으면 `multiSelect: true` 로 묻는다(예: "다 만들어줘" 같은 답을 자유롭게 받을 수 있게).
   - 이 질문은 **범위 확정**이 목적이며, 컨설팅 초안 승인 질문(원칙 1의 단일 선택 승인)이나 2단계의 스킬/에이전트/DMN 후보 선택과는 다른 별개의 질문이다.
5. 사용자가 하나를 고르면 그 프로세스에 대해 **평소의 1단계**(흐름 초안 제안 → 승인)를 정상 진행한다. 여러 개를 골랐다면 [11-multi-process.md](11-multi-process.md)의 절차로 각각 처리한다.

## BPMN 규칙에 맞는 흐름 만들기 (초안 품질)

초안은 그냥 단계 나열이 아니라 **나중에 유효한 BPMN이 될 수 있는 흐름**이어야 한다. 초안 단계에서 의식할 것:

- **시작과 끝이 분명**해야 한다 (시작 트리거 → … → 종료).
- 각 단계는 **한 역할(담당자)이 하는 하나의 작업**으로 쪼갠다.
- **분기(갈림길)** 가 있으면 명확히 한다: 예) "검토 → 승인이면 발송, 반려면 재작성으로 돌아감".
- 되돌아가는 흐름(반려 시 재작성 등)도 표현한다.
- 반복되거나 독립적인 묶음은 **서브프로세스**(하위 흐름)로 묶을 수 있다고 안내한다. (자세한 규칙은 2단계)

BPMN 에 익숙하지 않은 사용자도 이해하도록 이 모든 걸 자연어로 풀어 설명하고, 게이트웨이/시퀀스 같은 용어는 "갈림길", "화살표"처럼 풀어 쓴다(별도 모드 구분 없음 — 항상 동일).

## 산출물: `.bpmn/01-consulting.md`

합의가 되면 다음을 저장한다 (사용자 작업 디렉토리의 `.bpmn/01-consulting.md`, `Write` 도구 사용):

```markdown
# 컨설팅 요약

**프로세스 수**: 1개 / 여러 개
**프로세스명**: (한글)
**한 줄 설명**:

## 합의된 흐름 초안
1. ~ 단계 (역할: ~)
2. ~ 단계 (역할: ~)
3. 분기: ~ 인 경우 → A단계 / ~ 아닌 경우 → B단계
...

## 역할 / 담당자
- 역할1: (하는 일)
- 역할2: ...

## 입력/산출 데이터 (파악된 것)
- ~ 단계: 입력 (~), 산출 (~)

## 메모 / 미결 사항
- (예: "서브프로세스로 묶을 후보: VIP 뉴스레터 작성·리뷰")
```

이 파일은 2단계 JSON 생성의 **직접 입력**이 됩니다. 흐름·역할·데이터·분기를 빠짐없이 적어두면 JSON 품질이 올라갑니다.

## 다음 단계 연결

사용자가 초안에 동의하고 "생성할까요?" 에 확인하면:

> "좋습니다. 이제 합의한 흐름을 우리 서비스 규격의 **프로세스 정의(JSON)** 로 생성하겠습니다. 이건 자동으로 진행되고, 끝나면 어떤 단계·역할·분기가 만들어졌는지 요약해 드릴게요."

그리고 [02-generate-definition.md](02-generate-definition.md) 를 로드해 2단계로 진입합니다.
