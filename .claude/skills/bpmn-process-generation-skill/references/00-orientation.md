# 00 – Orientation: 진입 판별 + 요청 형태

이 단계는 *프로세스 생성 단계의 일부가 아닙니다*. 본 작업을 시작하기 전에 **이 사용자에게 어떻게 진행할지**를 빠르게 정하는 메타 단계입니다. 길게 끌지 마세요 — 보통 한두 문장 판단 후 바로 1단계(컨설팅)로 넘어갑니다.

## 왜 필요한가

같은 "프로세스 만들기"라도 사용자 상황이 다릅니다:

- "휴가 신청 프로세스 만들어줘" → 흐름이 명확. 바로 초안 제안하고 빠르게 진행.
- "우리 회사 구매 결재 자동화하고 싶어" → 어느정도 정보 있음. 초안 제안 후 1~2개 질문으로 다듬기.
- "영업이익 10% 올리고 싶어" → **흐름 정보 없음.** 바로 프로세스를 추측해 만들면 안 됨. 현황부터 질문.
- "우리 회사에 필요한 프로세스 추천해줘" / "홈페이지 보고 어떤 프로세스가 필요할지 알려줘" → **어떤 프로세스인지조차 없음.** 흐름은 물론 대상 업무 자체를 추측하지 말고, 회사 홈페이지 URL을 물어 그 내용을 근거로 후보를 제시한다. (자세한 절차는 [01-consulting.md](01-consulting.md)의 "회사 홈페이지 기반 프로세스 추천" 참고)
- "이어서 하자" / "폼 만들어줘" → 이미 진행 중. 재개 또는 특정 단계 진입.

## 판별 절차 (첫 응답에서 빠르게)

### 0. 문서 첨부 여부 먼저 확인 (최우선)
사용자가 **파일을 첨부/업로드**했거나, **파일 경로/이름을 언급**했거나, **긴 절차 텍스트를 붙여넣었다면** → 흐름을 추측하기 전에 [10-document-intake.md](10-document-intake.md) 로 가서 **문서를 먼저 읽고** 그 내용으로 흐름을 추출한다. 문서가 있으면 컨설팅 품질이 크게 올라가므로 이 확인을 가장 먼저 한다. 문서 신호가 없으면 아래 1~3 으로 진행한다.

### 0-1. 프로세스 개수 판별 (문서·요청을 본 직후)
문서를 읽거나 요청을 파악한 뒤, **만들 프로세스가 1개인지 2개 이상인지**를 가린다:
- **한 문서에 별개 프로세스가 여러 개**(서로 다른 제목·장·SOP, 각자 독립된 시작/종료·목적), **여러 문서 업로드**, 또는 사용자가 **여러 프로세스를 요청** → 2개 이상이면 [11-multi-process.md](11-multi-process.md) 로 가서 **인벤토리 → 범위 확정**부터 한다.
- 별개 프로세스인지 한 프로세스의 서브프로세스/단계인지 애매하면 11단계의 "별개 프로세스 vs 서브프로세스" 기준으로 가르고, 그래도 애매하면 1회만 확인한다.
- **1개뿐이면** 멀티 프로세스 reference 를 타지 않고 아래 1~3 으로(평소대로) 진행한다.

### 1. 진입 패턴 확인
- **신규 시작**인가, **세션 재개**(`.bpmn/` 에 산출물 존재)인가, **특정 단계 직접 호출**인가?
  - `.bpmn/process-definition.json` 이 있으면 재개로 본다. 어디까지 됐는지 요약하고 다음 단계 제안.
- 신규 시작이면 아래 2·3 으로.

### 2. 정보 충분도 판단
사용자의 첫 메시지에 **만들고 싶은 업무의 흐름을 추측할 단서**가 있는가?

- **충분/어느정도 있음** (예: "휴가 신청", "비품 구매 결재", "신규 입사자 온보딩") → 1단계로 가서 **흐름 초안을 먼저 제안**한다. 추측 가능한 일반적 흐름이 있으면 그걸 초안으로 만들고 사용자에게 보여준 뒤 다듬는다.
- **불충분(목표만 있음)** (예: "영업이익 올리고 싶어", "업무 효율화하고 싶어", 목표만 있고 절차가 없음) → **흐름을 지어내지 말고** 현재 어떤 업무를 어떻게 하는지부터 한 가지씩 묻는다. 목표치/방향성을 받으면 그에 맞는 프로세스를 *함께* 찾아간다. (자세한 규칙은 [01-consulting.md](01-consulting.md))
- **불충분(대상 업무조차 없음, 추천 요청)** (예: "어떤 프로세스가 필요한지 추천해줘", "우리 회사에 맞는 프로세스 뭐가 있을까") → 절차는 물론 **어떤 업무를 다룰지도 모름.** 프로세스를 지어내지 말고, 회사 홈페이지 URL을 받아 그 내용을 근거로 후보를 제시한 뒤 사용자가 고른 것부터 정상적으로 1단계를 시작한다. (절차는 [01-consulting.md](01-consulting.md)의 "회사 홈페이지 기반 프로세스 추천")

### 3. 요청 형태 판별 (단일 vs 여러 프로세스)
초심자/숙련자 같은 **모드 구분은 없다.** 누구에게나 동일하게, 용어는 자연스럽게 풀어 설명하며 진행한다. 다만 **요청이 프로세스 몇 개를 만드는지**만 가른다:

- **단일 프로세스**(자연어 1건 또는 문서 1건에 흐름 1개) → 평소대로 `.bpmn/` 플랫 구조로 5단계.
- **여러 프로세스**(한 문서/요청에 독립 프로세스 2개 이상, 또는 여러 문서·여러 자연어 요청) → [11-multi-process.md](11-multi-process.md) 의 고정 일괄 절차로. 프로세스별 네임스페이스로 분리한다.

> 문서/자연어, 단일/다중 어떤 형태든 **같은 5단계**를 적용한다(요청에 맞춰 프로세스 수만큼 반복). 형태에 따라 분기되는 것은 "프로세스 1개냐 여러 개냐" 뿐이다.

## "그냥 바로 만들어줘" 라고 할 때

사용자가 흐름을 충분히 설명했고 "질문 그만하고 바로 생성해" 라고 하면 → 컨설팅을 짧게 마무리(초안 한 번 보여주고 확인)한 뒤 2단계로 갑니다. 컨설팅 프롬프트 원칙상 **언제든 사용자가 원하면 바로 생성 가능**하다고 안내해야 합니다. 단, 정보가 정말 부족하면(2의 "불충분") 최소한의 핵심 질문 1~2개는 받는 게 좋습니다.

## 이미 `.bpmn/` 산출물이 있는 경우

새로 시작하지 말고 기존 `process-definition.json` 과 산출물을 요약해 "여기까지 됐는데, 다음으로 [다음 단계] 를 할까요, 아니면 수정할 부분이 있나요?" 라고 묻습니다.
