# 11 – Multi-Process: 여러 프로세스를 한 세션에서 생성

**목적**: 작업 범위에 **독립된 프로세스가 2개 이상** 있을 때(=한 문서에 별개 프로세스 여러 개, 여러 문서 업로드, 또는 사용자가 여러 프로세스를 요청), 각 프로세스를 **각각 컨설팅 → JSON 생성 → 아티팩트 선택 → 폼·참조정보**까지 빠짐없이 완성한다. pdf2bpmn 이 한 문서에서 여러 프로세스를 뽑아내던 동작을 이 skill 로 가져온 것이다.

> **절차는 고정이다(일관된 UX).** 진행 방식을 사용자에게 묻지 않는다 — 멀티 프로세스는 **항상 "일괄(batch)"** 로 §4 의 고정 절차를 그대로 따른다. (이전에 있던 "순차 vs 일괄 선택" 질문은 제거됨.) 사용자에게 묻는 것은 **(1) 어떤 프로세스를 만들지(§2)** 와 **(2) 프로세스별 아티팩트 선택(§4 4단계)** 뿐이다.

> 이 reference 는 0단계(orientation)·10단계(document-intake) 에서 **"프로세스가 2개 이상"** 으로 판별됐을 때 진입한다. 프로세스가 1개뿐이면 이 reference 를 타지 않고 평소대로(`.bpmn/` 플랫 구조) 진행한다.

---

## 1. 언제 이 단계를 타나 (멀티 프로세스 신호)

다음 중 하나라도 해당하면 멀티 프로세스 절차로 진입한다:

- **한 문서 안에 별개 프로세스가 여러 개** 있다. (서로 다른 제목·장(章)·SOP, 각자 독립된 시작/종료·목적)
- 사용자가 **여러 문서를 업로드**했고, 각 문서가 서로 다른 프로세스다.
- 사용자가 **여러 프로세스를 한 번에 요청**한다. 예: "구매 결재랑 출장 신청 둘 다 만들어줘".

### 별개 프로세스 vs 서브프로세스 (반드시 구분)
- **별개 프로세스**: 자기만의 트리거·종료·업무 목적·역할 묶음을 가지며 **독립적으로 실행 가능**하다 → 각각 별도 `process-definition.json`.
- **서브프로세스**: 하나의 큰 end-to-end 흐름의 **일부**다(부모 프로세스 안에 속함) → 별개 프로세스가 아니라 부모의 `subProcesses` 로 ([02-generate-definition.md](02-generate-definition.md)).
- 판별 기준: **하나를 떼어내도 다른 하나의 시작→종료가 깨지지 않으면** 서로 별개 프로세스다.

판별이 애매하면 사용자에게 1회만 확인한다: *"이 둘은 별개 프로세스로 각각 만들까요, 아니면 한 프로세스의 하위 단계로 묶을까요?"*

---

## 2. Phase 0 — 인벤토리 & 범위 확정 (사용자 개입: "만들 프로세스 선택" 1회)

흐름을 만들기 전에, 발견한 프로세스를 **번호 목록**으로 정리해 보여주고 **어떤 프로세스를 만들지만** 정한다. (진행 방식은 묻지 않는다 — 항상 §4 일괄 고정.)

### 2-1. 프로세스 인벤토리 제시
문서를 읽은 뒤(10단계), 발견한 **독립 프로세스를 번호로 나열**한다. 각 항목은 1줄(이름 + 트리거→목적).

### 2-2. 범위 질문 (`AskUserQuestion` 1회)
**`AskUserQuestion` 한 번**으로 묻는다(프로즈로 끝내지 말 것 — 질문 도구로 멈춰야 같은 세션 유지). 발견한 프로세스가 **4개 이하**면 `AskUserQuestion` 의 구조화된 옵션(각 옵션 `label`=프로세스명, `description`=트리거→목적)으로 그대로 나열하고 `multiSelect: true` 로 묻는다:

```
AskUserQuestion(questions=[{
  "question": "업로드하신 문서에서 독립된 프로세스 3개를 발견했어요. 어떤 프로세스를 만들까요? (전부 선택이 기본)",
  "header": "만들 프로세스",
  "multiSelect": true,
  "options": [
    {"label": "구매 결재", "description": "구매요청 접수 → 검토·승인 → 발주"},
    {"label": "출장 신청", "description": "출장계획 제출 → 팀장 승인 → 정산"},
    {"label": "비품 반납", "description": "반납요청 → 확인 → 자산 회수"}
  ]
}])
```

발견한 프로세스가 **5개 이상**이면(도구 옵션 상한 4개 초과) 옵션 나열 대신, 질문 텍스트에 **번호 목록**으로 전체를 제시하고 옵션은 진행 범위만 고르게 한다(구체 번호는 "Other" 자유 입력으로 받는다):
```
AskUserQuestion(questions=[{
  "question": "업로드하신 문서에서 독립된 프로세스 6개를 발견했어요:\n1. ...\n2. ...\n...\n6. ...\n어떤 프로세스를 만들까요?",
  "header": "만들 프로세스",
  "multiSelect": false,
  "options": [
    {"label": "전체 진행", "description": "발견한 프로세스 전부를 만듭니다"},
    {"label": "일부만 선택", "description": "만들 프로세스 번호를 직접 입력해 주세요(예: 1, 3, 5)"}
  ]
}])
```

> 진행 방식(순차/일괄)은 **묻지 않는다.** 선택된 프로세스는 §4 의 고정 일괄 절차로 진행한다. 처리 순서는 **문서 등장 순서**(= 인벤토리 번호 순). 사용자가 순서를 바꾸고 싶다고 하면 그때만 반영한다.

### 2-3. 인벤토리 저장
선택 결과를 `.bpmn/index.md` 에 저장한다(아래 "인벤토리 파일" 템플릿). 이 파일이 멀티 프로세스의 **진행 상태 추적기**가 된다.

---

## 3. 산출물 보관 — 프로세스별 네임스페이스

프로세스가 2개 이상이면 충돌을 막기 위해 **프로세스마다 하위 폴더**를 둔다:

```
.bpmn/
├── index.md                        # 인벤토리 + 진행상태 표 (멀티 프로세스 전용)
├── 01-<slug>/
│   ├── 01-consulting.md
│   ├── process-definition.json
│   ├── skills/<safe-name>/SKILL.md
│   └── forms/<activity_id>.html
├── 02-<slug>/
│   └── ... (동일 구조)
└── ...
```

- `<slug>`: 프로세스명 기반 kebab-case 영문(또는 로마자) 짧은 식별자. 예: `01-purchase-approval`, `02-trip-request`.
- **프로세스가 1개뿐이면 하위 폴더를 만들지 않고** 기존처럼 `.bpmn/` 플랫 구조를 쓴다(하위 호환).
- 각 단계 reference 가 말하는 `.bpmn/process-definition.json`·`.bpmn/forms/`·`.bpmn/skills/` 는 멀티 프로세스에선 **`.bpmn/<NN>-<slug>/` 아래의 같은 경로**로 읽는다.

### 인벤토리 파일 (`.bpmn/index.md`) 템플릿
```markdown
# 프로세스 인벤토리

**출처**: (문서명/요청 요약)
**진행 방식**: 일괄(고정)

| # | 프로세스 | 폴더 | 상태 |
|---|----------|------|------|
| 1 | A 프로세스 | 01-a-process | 완료 |
| 2 | B 프로세스 | 02-b-process | 컨설팅중 |
| 3 | C 프로세스 | 03-c-process | 대기 |
```

상태 값: `대기` → `컨설팅중` → `정의생성` → `아티팩트` → `폼·참조` → `완료`. **각 프로세스가 단계를 넘을 때마다 이 표를 갱신**한다.

---

## 4. 고정 절차 (항상 일괄 진행)

선택된 프로세스들을 **항상 아래 순서 그대로** 진행한다. 단계 순서·진행 방식을 사용자에게 묻지 않는다(일관된 UX). 각 단계는 모든 선택 프로세스를 **한꺼번에(batch)** 처리하고 다음 단계로 넘어간다.

### 4단계 절차

1. **컨설팅 일괄** — 선택된 **모든 프로세스의 흐름 초안**을 [01-consulting.md](01-consulting.md) 규칙으로 만들어, **한 메시지에 번호로 구분(`### 1/N · A 프로세스`, `### 2/N · B 프로세스` …)** 해 전부 제시한다(`AskUserQuestion` 으로 승인받는다 — 전체 승인/일부 수정 두 옵션이면 충분하고, 구체 수정 내용은 "Other" 자유 입력으로 받는다). 각 초안은 그 프로세스의 `.bpmn/<NN>-<slug>/01-consulting.md` 에 저장한다. 문서로 못 채운 빈칸이 있으면, 그 질문도 **번호로 묶어 같은 메시지에** 함께 낸다(프로세스별로 1~2개만). index.md 상태 모두 `컨설팅중`.
2. **사용자 일괄 응답** — 사용자는 **한 번에** 전부 승인하거나, "2번은 ~ 바꿔줘" 처럼 **번호로** 수정/답변한다. 수정 요청이 있으면 해당 번호 초안만 고쳐 다시 보여주고 다시 일괄 확인을 받는다. (개별 프로세스만 따로 떼어 진행하지 않는다.)
3. **JSON 일괄 생성** — 승인된 모든 초안을 [02-generate-definition.md](02-generate-definition.md) 규칙으로 각각 `.bpmn/<NN>-<slug>/process-definition.json` 으로 **한꺼번에 생성**한다. index.md 상태 모두 `정의생성`. 생성 결과는 프로세스별 한 줄씩만 짧게 보고.
4. **아티팩트 일괄 질문 (프로세스별 패널)** — 각 프로세스의 [03-elicit-artifacts.md](03-elicit-artifacts.md) 후보를 도출해, **프로세스마다 별도 `AskUserQuestion` 호출**(스킬/에이전트/DMN 후보를 종류별 질문의 `options`로 구조화, `multiSelect: true`)을 **연달아** 실행한다. 각 호출의 `question` 앞머리에 **"[k/N: <프로세스명>]"** 라벨을 붙여 어느 프로세스 질문인지 분명히 한다. **모든 프로세스의 선택을 다 받은 뒤** 5단계로 간다. index.md 상태 모두 `아티팩트`.
5. **이후 단계 일괄 실행** — 모든 프로세스에 대해 아티팩트 생성 → 폼 → 참조정보를 **추가 질문 없이 일괄 자동 실행**한다(폼·참조정보는 어떤 프로세스든 항상 생성). 끝나면 index.md 상태 모두 `완료` → §7 최종 통합 요약. 이어서 각 프로세스를 검증·완료([09-service-execution.md](09-service-execution.md))한다.

### 아티팩트 선택 원칙 (자동 적용·자동 스킵 금지)
4단계의 프로세스별 패널은 **반드시 직접 묻는다.** 앞 프로세스의 선택을 뒤에 자동 적용하거나, 묻지 않고 추천을 자동 수락하지 않는다. 이유:
- 추천 후보는 **그 프로세스의 elements(액티비티·게이트웨이)에서 도출**된다. 프로세스가 다르면 후보가 전혀 다르므로 "그대로 적용"은 의미가 성립하지 않는다.
- 묻지 않고 자동 수락하면 선택 단계의 존재 이유인 **HITL 이 사라진다**(= 사용자 동의 없이 아티팩트를 다 만드는 것 = 스킬 금지 행위).
- 비용은 작다: 사용자 개입은 전체에서 **컨설팅 일괄 응답 1회 + 프로세스별 아티팩트 패널 N회** 뿐. 아무것도 안 고른 프로세스는 스킬·에이전트·DMN 없이 폼·참조정보만으로 진행(기존 선택 단계 규칙과 동일).

## 5. 프로세스 간 재사용 (스킬·에이전트)

> 이것은 "자동 적용"(§4 아티팩트 선택 원칙에서 금지)과 다르다. 아티팩트를 **만들지 말지·무엇을 만들지는 프로세스마다 사용자가 고른다.** 다만 사용자가 고른 결과가 앞 프로세스에서 이미 만든 것과 **동일 의도**로 판명되면, 같은 것을 두 번 만들지 않고 기존 산출물을 연결할 뿐이다(중복 제거).

여러 프로세스가 **같은 의도의 스킬/에이전트**를 선택했다면 중복 생성하지 않는다:
- 앞 프로세스에서 이미 만든 스킬(같은 `safe_name`/의도)·에이전트(같은 `agent_id`)가 뒤 프로세스에서도 선택되면 **그대로 재사용**(JSON 의 `skills[]`/`activity.skills`/`activity.agent` 에 기존 id 연결)하고, 사용자에게 "기존 스킬 재사용" 으로 알린다.
- 재사용 스킬 파일은 **하나만** 두고(예: 첫 등장 프로세스 폴더, 또는 `.bpmn/_shared/skills/`), 여러 프로세스가 그 id 를 참조하게 한다. 정책은 일관되게 유지하고 `index.md` 에 메모한다.

---

## 6. 세션 재개 (멀티 프로세스)

"이어서 하자" 로 돌아오면:
1. `.bpmn/index.md` 의 상태 표를 읽는다.
2. "1·2 완료, 3 컨설팅중, 4 대기" 처럼 **전체 진행 상황을 요약**한다.
3. 고정 절차(§4) 상 다음에 와야 할 단계부터 이어간다(예: 모두 `정의생성`이면 4단계 아티팩트 패널부터). 어디부터 할지 사용자가 바꾸고 싶어 하면 1회 확인.

---

## 7. 최종 통합 요약 (모든 프로세스 완료 후)

모든 선택 프로세스가 끝나면 **한 번에** 통합 보고한다:

```
요청하신 프로세스 N개를 모두 완성했어요!

1. **A 프로세스** — 단계 n개 / 분기 n개 · 스킬 n · 에이전트 n · DMN n · 폼 n개  (.bpmn/01-a-process/)
2. **B 프로세스** — …  (.bpmn/02-b-process/)
...

전체 인벤토리·진행상태: .bpmn/index.md
특정 프로세스를 수정하고 싶으면 "2번 ~" 처럼 번호로 말씀해 주세요.
```

- 프로세스별 산출물 경로(`.bpmn/<NN>-<slug>/`)를 분명히 보여준다.
- 수정 요청은 번호 기준으로 받는다.

---

## 8. 주의

- **인벤토리에서 합의된 개수만큼만** 만든다. 문서에 잠깐 언급된 것을 임의로 별개 프로세스로 늘리지 않는다(서브프로세스/단계일 수 있음 — 08단계 reference 메모로 남기고 확인).
- 각 단계에서 **장문 중간 요약을 반복하지 않는다.** 단계별로 프로세스당 한 줄 + 진행 라벨([k/N])만, 최종에 한 번 통합 요약(§7).
- 고정 절차(§4)의 단계 순서를 건너뛰거나 섞지 않는다 — 컨설팅 일괄 → 일괄 응답 → JSON 일괄 생성 → 아티팩트 패널(프로세스별) → 이후 일괄 실행 순서를 그대로 지킨다.
- 멀티 프로세스라고 단계 규칙(02~08)을 느슨하게 적용하지 않는다 — 각 프로세스는 단일 프로세스와 동일한 품질·구조로 만든다.
- 서비스(ProcessGPT deepagent) 모드에서는 **프로세스별 JSON 산출물 N개**를 반환한다([09-service-execution.md](09-service-execution.md) 의 출력 계약을 프로세스마다 1개씩).
