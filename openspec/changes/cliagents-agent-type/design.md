## Context

ProcessGPT 의 에이전트 실행은 워크아이템에 기록된 오케스트레이션 값에 따라 전용 서비스가 폴링해 처리하는 구조다(`deepagents`, `langchain-react`, `a2a` 등). `deepagents` 서비스는 LangChain deepagents/LangGraph 위에서 스킬 로딩, MCP 도구, 서브에이전트, HITL 인터럽트, 체크포인트 재개, 채팅 SSE, 파일 산출물 전달, 결정적 재실행까지 제공하는 가장 완성도 높은 오케스트레이션이다.

이번 변경은 같은 사용자 가치를 **CLI 코딩 에이전트(Claude Code, Codex)** 위에서 제공하는 새 오케스트레이션을 추가한다. 근거가 되는 `cliagents` 라이브러리는 이미 세 표면(터미널 실행, 프로젝트 아티팩트, 커맨드/MCP 브리지)을 provider 전략으로 통합해 두었고, 의존성이 없는 표준 라이브러리 전용 패키지다. 다만 현재 터미널 표면은 **대화형 PTY 세션 실행만** 제공하므로, 업무 위임에 필요한 비대화형 실행 경로가 없다.

제약:

- CLI 에이전트는 자체 프로세스·자체 인증·자체 도구를 갖는 블랙박스다. 우리가 관측할 수 있는 것은 표준출력 이벤트 스트림, 워크스페이스 파일 변화, 우리가 등록한 MCP 서버 호출뿐이다.
- 두 CLI 는 지시문 파일명, 스킬 배치 경로, MCP 등록 범위(프로젝트 vs 사용자 전역)가 서로 다르다.
- 서비스는 컨테이너에서 다수 테넌트의 업무를 동시에 처리하므로, 사용자 전역 설정에 의존하는 부분은 실행 단위로 격리해야 한다.

## Goals / Non-Goals

**Goals:**

- 사용자가 업무/에이전트 단위로 `cliagents` 오케스트레이션과 실행 CLI(claude-code/codex)를 선택해 업무를 위임할 수 있다.
- `deepagents` 와 동등한 실행 계약(초안/완료 모드, 진행 스트리밍, HITL, 파일 산출물, 스킬, MCP 도구, 재실행/되돌리기)을 제공한다.
- CLI 별 분기는 `cliagents` provider 안에서만 존재하고, ProcessGPT 서비스 코드에는 "어느 CLI 인가" 분기가 남지 않는다.
- 새 CLI 에이전트 추가는 provider 하나 추가로 끝난다.

**Non-Goals:**

- `deepagents` 오케스트레이션 대체·폐지. 두 오케스트레이션은 공존하며 사용자가 선택한다.
- CLI 에이전트 내부 동작(모델 선택 로직, 도구 구현, 컨텍스트 관리) 재현·대체.
- ProcessGPT 도구를 LangChain 도구로 다시 구현. 도구 노출은 MCP 로 통일한다.
- 브라우저에서 CLI 터미널을 직접 조작하는 대화형 터미널 UI(라이브러리의 터미널 표면은 이번 범위에서 쓰지 않는다).

## Decisions

### 1. 서비스 배치 — 라이브러리와 서비스를 별도 저장소로 나눈다

두 개의 서브모듈을 둔다.

| 경로 | 저장소 | 역할 |
| --- | --- | --- |
| `services/cliagents` | uengine-oss/cliagents | CLI 에이전트 전략 라이브러리. 표준 라이브러리만 사용한다. |
| `services/cli-agent` | uengine-oss/process-gpt-cli-agent | ProcessGPT 에이전트 타입 서비스. 위 라이브러리의 소비자다. |

라이브러리와 서비스를 한 저장소에 두면 headless 표면 변경과 그 소비자 변경이 한 커밋에 묶이는 이점이 있지만, 대가가 더 크다. 라이브러리는 "설치해도 아무것도 딸려오지 않는다"가 존재 이유이고, 서비스는 에이전트 SDK·웹 프레임워크·Supabase 를 끌고 온다. 두 의존성 정책이 한 저장소에 살면 경계는 규칙이 아니라 습관이 되고, 편의를 위한 import 하나씩 무너진다. 또한 다른 ProcessGPT 서비스가 모두 독립 저장소 + 서브모듈이므로 배포·버전·이슈 추적이 같은 방식으로 동작해야 한다.

경계는 라이브러리 쪽 테스트가 기계적으로 지킨다(`tests/test_library_has_no_dependencies.py`: `src/cliagents` 의 모든 모듈은 표준 라이브러리와 자기 형제 모듈만 import 할 수 있다).

서비스는 라이브러리를 git 의존성으로 참조한다. 프로덕션 롤아웃 전에는 태그로 고정한다.

- 대안 A(한 저장소에 둘 다): 위 이유로 기각.
- 대안 B(모노레포 내 일반 디렉터리): 다른 서비스와 배포·버전 관리 방식이 어긋난다.

### 2. headless 실행은 `cliagents` 의 새 표면으로 올린다

provider 계약에 실행 표면을 추가한다. 표면은 세 가지를 책임진다.

1. **실행 argv 구성** — 프롬프트, 작업 디렉터리, 모델, 권한 수준, 세션 이어가기 식별자를 받아 CLI 별 비대화형 실행 명령을 만든다(Claude Code 는 출력 형식을 구조화 스트림으로 지정하는 인쇄 모드, Codex 는 비대화형 exec 의 JSON 출력 모드).
2. **이벤트 정규화** — CLI 가 뱉는 서로 다른 JSON 라인을 공통 이벤트로 변환한다.
3. **세션 식별자 추출/재개** — 실행 결과에서 이어가기용 세션 식별자를 뽑고, 다음 실행에서 그것으로 재개한다.

PTY 화면을 파싱하는 방식은 채택하지 않는다. 터미널 렌더링(스피너, ANSI, 화면 재그리기)은 결과 파싱의 안정적인 근거가 될 수 없다. 반대로 서비스 안에만 어댑터를 두는 방식도 채택하지 않는다 — 그러면 "어느 CLI 인가" 분기가 라이브러리 밖으로 새어나가 라이브러리의 존재 이유가 무너진다.

### 3. 공통 이벤트 스키마는 프론트가 이미 아는 SSE 이벤트로 매핑한다

정규화 이벤트는 최소 다음을 구분한다: 실행 시작, 어시스턴트 텍스트 증분, 도구 시작/종료, 계획 갱신, 사용자 확인 요청, 파일 변경, 토큰/비용 사용량, 최종 결과, 오류.

서비스는 이것을 `deepagents` 가 이미 내보내는 SSE 이벤트 이름(`tool_start`, `tool_end`, `plan_*` 등)으로 그대로 매핑해 내보낸다. 프론트의 스트리밍 렌더링을 새로 만들지 않기 위해서다. CLI 고유 정보(세션 식별자, 원본 이벤트 타입)는 payload 안에 부가 필드로 싣는다.

### 4. 도구는 MCP 로만 노출한다

ProcessGPT 도구(프로세스/폼/메멘토/오피스/스토리지)는 CLI 에이전트에 MCP 서버로 붙인다. 실행 전 브리지 설치는 멱등적이어야 하고, 사용자가 직접 넣은 등록을 지우면 안 된다.

Codex 는 MCP 등록이 사용자 전역 설정에 들어간다. 다중 테넌트 동시 실행에서 전역 설정을 공유하면 테넌트 간 도구/자격 증명이 섞인다. 따라서 **실행마다 Codex 홈 디렉터리를 격리**해 전역 등록이 그 실행에만 적용되도록 한다. 이 격리는 서비스가 아니라 provider 가 아는 사실(등록 범위)에 근거해 선택된다.

### 5. 스킬은 실행 워크스페이스에 아티팩트로 emit 한다

업무 지시문(시스템 프롬프트에 해당), 테넌트 스킬, 번들 시스템 스킬, git 에서 가져온 스킬을 하나의 아티팩트 번들로 모으고, 선택된 provider 가 자기 관례에 맞는 경로로 써 넣는다(Claude Code 는 루트 지시문 파일 + 스킬 디렉터리, Codex 는 다른 파일명 + 스킬별 디렉터리와 필수 frontmatter).

스킬 자산의 원본(테넌트 업로드본, git 원본)은 CLI 중립 형태로 보관하고, CLI 별 변환은 emit 시점에만 일어난다. 같은 스킬이 두 CLI 에서 모두 동작해야 하며, 한쪽에서 지원하지 않는 아티팩트 종류는 조용히 버리지 않고 "건너뜀"으로 보고한다.

### 6. HITL 은 그래프 인터럽트가 아니라 "세션 일시정지 + 재개"로 구현한다

`deepagents` 는 LangGraph 인터럽트와 체크포인터로 중단/재개를 표현한다. CLI 에이전트에는 그런 체크포인트가 없다. 대신:

- CLI 가 확인 요청/추가 입력 요청 이벤트를 내보내거나 실행이 승인 대기로 끝나면, 서비스는 사용자 확인 요청을 발행하고 실행을 종료 상태가 아닌 **대기 상태**로 표시한다.
- 대기 상태는 (세션 식별자, 워크스페이스 경로)로 표현되어 저장된다.
- 사용자가 응답하면 같은 워크스페이스에서 세션 재개 실행을 시작하고, 사용자의 응답을 새 입력으로 넣는다.

따라서 워크스페이스와 세션 식별자는 실행 종료 후에도 일정 기간 보존되어야 하며, 서비스 재시작에도 살아남도록 영속 볼륨에 둔다.

### 7. 권한과 격리는 설정 계약으로 노출한다

CLI 에이전트는 파일 쓰기와 명령 실행 권한을 갖는다. 선택 가능한 권한 수준(읽기 전용 / 워크스페이스 쓰기 허용 / 명령 실행 허용)을 오케스트레이션 설정으로 노출하고, provider 가 그것을 CLI 별 플래그로 번역한다. 기본값은 "워크스페이스 안에서만 쓰기 허용"이며, 그 이상은 명시적 선택을 요구한다.

### 8. 결정적 재실행은 관측 가능한 경계에서만 기록한다

CLI 내부의 모델 호출은 재현 대상이 아니다. 재실행/되돌리기의 기록 단위는 (a) 우리 MCP 서버를 통과한 외부 변경 호출과 (b) 워크스페이스 파일의 변경 전/후 스냅샷이다. CLI 내장 편집 도구로 워크스페이스 밖을 건드리는 경우는 권한 기본값에서 막는다. 이 경계는 `deepagents` 의 재실행이 커버하던 범위와 다르므로, 스펙에서 재실행 대상 범위를 명시적으로 정의한다.

### 9. 가용성은 조회 가능해야 하고, 대체 실행은 하지 않는다

CLI 미설치·미인증은 흔한 운영 실패다. 서비스는 설치·인증 가용성을 조회하는 경로를 제공하고, 프론트는 선택 시점에 이를 보여준다. 실행 시점에 CLI 가 없으면 다른 CLI 나 다른 오케스트레이션으로 조용히 대체하지 않고, 설치 안내가 포함된 실패로 업무를 종료한다(라이브러리의 "silent substitution 금지" 원칙과 일치).

### 10. 동시 실행 상한을 둔다

CLI 프로세스는 LangGraph 실행보다 무겁고(프로세스 + 파일시스템 + 자체 컨텍스트), 워크스페이스 디스크를 점유한다. 폴링 서버는 동시에 실행 중인 CLI 프로세스 수 상한을 갖고, 초과 시 워크아이템을 잡지 않는다.

## Risks / Trade-offs

- **CLI 출력 포맷 변경으로 파싱이 깨짐** → 정규화 계층을 provider 안 한 곳으로 모으고, 알 수 없는 이벤트 타입은 버리지 말고 원본 그대로 통과시켜 최소한 텍스트는 사용자에게 보이게 한다. CLI 버전을 이미지에 고정하고, 라이브 CLI 대상 계약 테스트를 둔다.
- **CLI 미인증/미설치로 실행 실패** → 가용성 조회 경로 + 기동 시 진단 로그 + 실패 메시지에 설치/로그인 안내. 조용한 대체는 하지 않는다.
- **Codex MCP 등록이 사용자 전역이라 테넌트 간 오염** → 실행별 홈 디렉터리 격리. 격리 실패 시 실행을 진행하지 않고 실패로 처리한다.
- **세션 재개 실패(세션 만료, 워크스페이스 소실)** → 재개 불가 시 사용자에게 "새 실행으로 이어감"을 명시하고, 직전 대화/산출물 요약을 새 프롬프트에 실어 재시작한다. 조용히 처음부터 다시 하지 않는다.
- **파일시스템/명령 실행 권한으로 인한 보안 노출** → 기본 권한을 워크스페이스 쓰기로 제한, 워크스페이스는 실행 단위 격리, 상향 권한은 명시적 설정. 자격 증명은 환경 변수로만 주입하고 워크스페이스에 쓰지 않는다.
- **비용 급증** → 사용량 이벤트를 실행 결과에 기록하고, 동시 실행 상한과 실행 타임아웃을 둔다.
- **`deepagents` 와 미묘하게 다른 동작으로 사용자 혼란** → 오케스트레이션 선택 화면에서 차이(비용 수준, 권한, 도구 방식)를 설명 문구로 노출한다.
- **두 저장소로 나뉘어 headless 표면 변경이 두 곳을 오간다** → 서비스는 라이브러리를 git 의존성으로 참조하고, 라이브러리 쪽에 두 provider 공통 계약 테스트를 두어 표면 변경이 소비자보다 먼저 검증되게 한다. 프로덕션 롤아웃 전에는 라이브러리 커밋을 태그로 고정한다.
- **결정적 재실행 범위가 `deepagents` 보다 좁음** → 스펙에서 재실행 가능 범위를 명시하고, 범위 밖 변경이 있었던 실행은 "부분 재실행 불가"로 표시한다.

## Migration Plan

1. `services/cliagents`(라이브러리)와 `services/cli-agent`(서비스) 서브모듈 추가 및 클론/초기화 문서화.
2. 라이브러리에 headless 실행 표면과 이벤트 정규화를 추가하고, 두 provider 구현 + 계약 테스트를 통과시킨다(CLI 미설치 환경에서는 건너뛰기).
3. 서비스 스켈레톤(폴링 서버 + 헬스 + 가용성 조회)을 올리고, 단순 업무 한 건이 끝까지 도는 경로를 먼저 완성한다.
4. 스킬 아티팩트 주입 → MCP 브리지 → 채팅 스트리밍 → 파일 산출물 → HITL → 재실행/되돌리기 순으로 계약을 채운다. 각 단계는 이전 단계 없이도 실행이 성공하는 상태를 유지한다.
5. 프론트엔드에 오케스트레이션 항목과 CLI 선택 필드를 추가하되, 가용성 조회가 실패하면 선택 불가로 표시한다.
6. 배포는 새 서비스만 추가되므로 기존 오케스트레이션에 영향이 없다. 롤백은 프론트에서 오케스트레이션 항목을 감추고 서비스를 내리는 것으로 충분하며, 이미 `cliagents` 로 지정된 워크아이템은 폴링되지 않고 대기 상태로 남는다(운영자가 다른 오케스트레이션으로 재지정 가능해야 한다).
