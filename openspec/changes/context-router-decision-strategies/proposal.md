## Why

사용자는 한 채팅창에서 여러 일을 섞어 말한다(유튜브 채널 확인, 출장 준비, 진행 중인 작업에 대한 후속 지시). 지금 ProcessGPT 는 메시지를 클라이언트가 지정한 하나의 대화로만 보내므로, 맥락이 섞이거나 사용자가 대화방을 직접 나눠야 한다. hark 같은 비서 UI 는 메시지마다 어느 일의 후속인지 판단해 각자의 맥락으로 답한다.

또 ProcessGPT 의 모든 판단(엔진의 다음 단계 결정, 라우터의 도구 선택)은 LLM 이 문장을 생성하고 그 JSON 을 파싱하는 방식뿐이라, 판단마다 수백 ms~수 초가 걸리고 확신도가 없어 "모호하면 묻기" 같은 정책을 세울 수 없다. 로그확률을 주는 모델에서는 한 토큰으로 선택지 분포를 얻을 수 있고, JEV 류의 전용 판단 모델(typed decision model)은 더 빠르고 저렴하다.

## What Changes

- 새 서비스 `services/context-router` 를 에이전트 앞단에 둔다. 에이전트(deepagents, cliagents)는 바꾸지 않는다.
- **판단 전략(전략 패턴)**: 공통 판단 계약(`POST /decide`)과 세 전략 — 판단 모델(judge) → logprob → JSON — 을 설정 순서대로 시도하고, 측정된 확신도가 낮으면 다음 전략으로 에스컬레이션한다. 판단 모델이 설정돼 있으면 최우선으로 쓴다.
- **참조 판단 서버**: 오픈 웨이트 모델의 선택지 문자 로짓으로 판단하는 서버(open-alternative-jev 기반)를 함께 제공한다.
- **대화 맥락 라우팅**: 채팅 메시지마다 사용자의 최근 맥락과 클라이언트가 보낸 맥락 중 어느 대화의 후속인지, 새 주제인지 판단해 `conversation_id` 를 정한다. 확신이 없으면 옮기지 않는다. 라우팅은 요청별 선택(`metadata.auto_route`)이다.
- **투명 프록시**: 라우팅한 채팅은 대상 에이전트로 전달하고 SSE 를 그대로 흘려보내며, 그 밖의 경로도 그대로 전달한다. 게이트웨이의 에이전트 경로만 바꾸면 앞단에 둘 수 있다.
- **맥락 저장**: 사용자별 맥락(제목·요약)을 `context_threads` 테이블에 기록한다.

## Capabilities

### New Capabilities

- `context-router_decision-strategies`: 선택지 중 하나와 확률을 돌려주는 판단 계약, 판단 모델 최우선 전략 체인, 확신도 에스컬레이션, logprob 가용성 자동 판별, 측정/자기 보고 확신도 구분, 판단 모델 엔드포인트 계약.
- `context-router_conversation-routing`: 메시지의 맥락 판단, 확신 부족 시 머물기, 요청별 선택 라우팅, 에이전트 앞 투명 프록시, 맥락 기억.

### Modified Capabilities

없음. 에이전트의 채팅 계약은 그대로이며, 라우터는 그 계약을 지키는 요청을 만들어 전달한다.

## Impact

- **신규 서비스**: `services/context-router`(포트 8895), 선택 구성으로 참조 판단 서버(포트 8896, GPU/Apple MPS 필요).
- **데이터**: `context_threads` 테이블 추가.
- **게이트웨이(선택)**: `process-gpt-deepagents` 경로를 라우터로 향하게 하면 앞단에 놓인다. 라우팅은 `metadata.auto_route` 를 보낸 요청에만 적용되므로 기존 대화방은 영향이 없다.
- **클라이언트**: 통합 채팅을 쓰는 클라이언트(pgpt-pro 메인 채팅)는 `auto_route` 와 맥락을 보내고, 응답 첫 `metadata` 이벤트의 라우팅 결과를 답변에 표시한다.
- **후속 적용 후보**: 엔진의 LLM 분기 판단, 클라이언트 라우터의 의도 분류, 브라우저 에이전트의 빠른 상태 판단(design 참조)이 같은 `POST /decide` 를 쓸 수 있다.
