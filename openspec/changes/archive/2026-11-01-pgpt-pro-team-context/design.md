## Context

Process GPT Lite 의 메인 채팅은 context-router 가 메시지마다 어느 대화 맥락으로 이어 갈지 정한다. 결과는 `context_threads`(사람마다 맥락 id, 제목, 「최근 요청·최근 답」 조각)다. 이 맥락은 지금까지 화면의 맥락 칩과 맥락 목록에만 쓰였다. 사용자가 원한 것은 세 가지다.

1. 나눈 맥락이 기억처럼 자동으로 참고되는 것
2. 팀원의 맥락도 요청 → 허락으로 참고되는 것. 기본은 허락이다
3. 관리자·팀원이 서로 무슨 일을 AI 와 하고 있는지 요약해서 보는 것

이 모두에 보안 계층이 필요하다. 한장(hanjang)에서 같은 개념을 먼저 설계했고, 그 판정 로직을 Lite 의 데이터에 맞게 옮겼다(사례 39개 그대로 통과).

## Goals / Non-Goals

**Goals**
- 공개 계층 하나(누구에게 × 얼마나 깊이 + 역할)를 자동 참고·요청·팀 활동·맥락 보기의 모든 경로가 똑같이 쓴다
- 턴의 지연이 체감되지 않게 한다(고르기 2초 상한, 실측은 수십~수백 ms)
- 이 기능 전의 사용자는 아무것도 바뀌지 않게 한다

**Non-Goals**
- 공유 폴더·프로젝트 단위의 등급(폴더는 이미 구성원 공유가 있다), 회사 밖 게스트
- context-router 의 맥락 나누기 자체를 바꾸는 것
- 프로세스 단계 모니터링(동작 보기)·Agentic BPM 리포트를 대체하는 것. 팀 활동은 그 옆에 사람 단위로 더한다

## Decisions

### 1. 공개 계층: 두 축 + 역할 덧씌움 (세 안 중 C)

| 안 | 내용 | 버린 이유 |
|---|---|---|
| A. 역할만 | 관리자 > 장 > 팀원, 위가 아래를 다 본다 | 개인 작업·인사 상담을 지킬 수단이 없다. 사람들이 AI 와의 대화를 회사 도구 밖으로 옮기고, 팀 인텔리전스가 생기지 않는다 |
| B. 맥락마다 사람 목록(ACL) | 가장 세밀하다 | 맥락은 하루에도 여러 개 생긴다. 아무도 목록을 관리하지 않고, 「다 열기」나 「다 닫기」로 수렴한다 |
| **C. 범위 × 깊이 + 역할** | 아래 표 | 채택 |

```
누구에게(범위)  나 ─ 팀 ─ 부서 ─ 회사          ← Process GPT 조직도(팀 노드·중첩)
얼마나 깊이      제목 ─ 요약 ─ 원문

등급                    제목      요약           원문
private  비공개         나        나             나
listed   제목 공개      회사      허락받은 사람   허락받은 사람
summary  요약 공개(기본) 회사      범위(팀)       허락받은 사람  ← 같은 팀은 기본 규칙으로 요청 즉시 자동 허용
open     전체 공개      회사      범위           범위

역할 덧씌움   장(팀·부서 노드) = 노드 아래의 private 아닌 맥락을 요약까지 / 관리자 = 회사 노드의 장, 원문은 관리자도 요청
민감 표시     open 금지 · 자동 허용 제외 · 장·관리자에게도 제목만 · 원문은 범위 안이어도 닫힘
비공개        존재도 숨김(id 로 불러도 404), 관리자에게는 건수만
```

- **제목은 회사 전체에 보인다**(`private` 제외). 그래야 다른 팀의 관련 맥락을 찾아 「요청하기」를 띄울 수 있다. 제목조차 보이면 안 되는 맥락은 `private` 로 둔다.
- **요청 후보와 겹침의 관련도는 보이는 깊이의 글로만 매긴다.** 볼 수 없는 원문으로 관련도를 매기면, 질문을 바꿔 가며 남의 원문을 떠볼 수 있다.

### 2. 기본값

새 맥락은 `summary`·`team` 이고, 자동 허용 규칙은 「같은 팀 → 원문까지 자동 허용(이 작업 동안)」이다. 사용자가 원한 흐름이 「요청하기 → 팀원이 기본으로 허락 → 그 맥락으로 일이 이어짐」이기 때문이다. 같은 팀은 한 번 누르면 원문까지 들어오고, 그 사실은 주인의 「쓰인 곳」과 하루 한 장의 모음 카드에 남는다. 다른 팀은 묻기다. 공유 규칙 행이 없는 사람은 `private` 로 다룬다. 그래서 이 기능을 켜지 않은 설치와 사람은 동작이 바뀌지 않는다.

### 3. 받은 맥락은 복사하지 않고 참조한다

pgpt-pro 의 산출물 공유(`pro_shares`)는 받은 사람 쪽에 사본을 만든다. 맥락에서 사본을 만들면 회수와 「쓰인 곳」 추적이 깨지므로, 허락 행과 참고 기록(출처)만 둔다.

### 4. 요약은 맥락마다 미리 만들고, 보는 사람에게는 조립만 한다

라우터의 `summary` 는 「최근 요청·최근 답」 원문 조각이라 요약 깊이에 쓸 수 없다. 그래서 맥락마다 `pro_context_digests` 를 만든다: 요약 2~3문장, 결정, 열린 질문, 작업 유형, 프롬프트 유형과 요청마다 바꿔 쓴 한 줄. 회사 게이트웨이 모델을 맥락마다 한 번 부르고, 요청 문장을 그대로 옮긴 줄은 버린다. 팀 활동 카드·겹침·인용 블록은 보는 사람의 깊이로 이 요약을 모으기만 한다. 보는 사람마다 모델을 부르지 않는다. 턴이 끝나면 그 맥락의 요약을 20초 뒤 다시 만든다.

### 5. 고르기와 판정

- 관련도는 judge 서버의 bge-m3 임베딩으로 매긴다. 맥락 글의 임베딩은 켜질 때와 5분마다 데워 두므로, 턴마다 새로 만드는 것은 메시지 하나다.
- 회색 구간은 회사 게이트웨이 모델에 「후보 기록이 지금 일에 직접 쓰이는가」를 묻는다. 생각을 끄고(`think: false`) 묻는다.
  - 생각을 켜면 1.6~1.8초가 걸려 쓸 수 없다. 끄면 0.15초다.
  - context-router 의 1단계 판정 모델(Qwen3-4B)은 이 질문에 「필요하다」를 너무 자주 골랐다(무관한 쌍 6개 중 3개).
- 맥락 나누기는 인용 블록이 아니라 원래 메시지로 한다(라우터 `route_text`).

측정(2026-11-01, 시드 회사 team-demo, 맥락 12개):

| 항목 | 값 |
|---|---|
| 고르기 | 첫 호출 0.2초, 데운 뒤 0.04~0.24초 |
| 요약 12개 만들기 | 15초 |
| 실제 턴 | 에이전트가 [1](내 맥락)·[2](팀원 맥락의 요약 깊이 결정)를 인용해 답함 |

### 6. Process GPT 에서 가져다 쓰는 것

| 필요한 것 | 이미 있는 것 | 이번에 한 것 |
|---|---|---|
| 맥락 | context-router `context_threads`, 답의 맥락 칩 | 등급·요약·턴 찾기(답의 `context.conversationId`, 새로 남기는 `conv` 표지) |
| 사람·팀·부서 | 조직도 `configuration['organization']` | 범위 계산. 장은 `pro_team_leads`(조직도 JSON 에 장 칸이 없다) |
| 관리자 | Lite `isAdmin`(users.is_admin·tenants.owner), Process GPT 역할 사다리 | 그대로 |
| 알림·결정 | `notifications` → Lite 홈 카드·알림 종·푸시 | 카드 안에서 허락·거절 |
| 뜻 비교·판정 | judge 임베딩, 회사 게이트웨이 모델 | 고르기·회색 구간·요약 |
| 진행 중인 AI 작업 | 대화 상태(working), 예약 작업, 프로세스 단계 | 사람 단위로 모음 |

## Risks / Trade-offs

- **[막아야 할 기존 공백] 원문이 PostgREST 로 열려 있다**(2026-11-01 공용 DB 에서 확인).
  - `pro_messages`, `pro_threads`, `context_threads` 는 RLS 가 꺼진 채 `authenticated` 에 SELECT 가 있다. 로그인한 누구나 PostgREST 로 다른 사람의 대화를 읽을 수 있고, 공개 등급은 BFF 경로에서만 지켜진다.
  - Lite 의 `pro_` 표 78개 중 57개가 같은 상태다(메일 계정·프로필·과금 포함).
  - deepagents 대화(`chats`)는 select 가 테넌트 전체에 열려 있다.
  - → 대응: 셋 모두 RLS 를 정책 없이 켠다(아래 SQL). Lite 화면과 라우터는 이 표를 PostgREST 로 읽지 않으므로 동작은 바뀌지 않는다. `chats` 는 참가자·관리자로 좁히는 Process GPT 업스트림 수정이 필요하다. 공용 DB 의 기존 표를 바꾸는 일이라 사람의 승인을 받고 적용한다.

    ```sql
    alter table pro_messages enable row level security;
    alter table pro_threads enable row level security;
    alter table context_threads enable row level security;
    ```
- **[답에 녹아든 내용]** 허락받은 맥락이 녹아든 답은 받은 사람의 기록이 된다. 출처는 남기지만, 받은 사람이 그 답을 더 넓게 공유하면 따라간다. → 출처 줄과 「쓰인 곳」으로 추적한다. 회수는 앞으로의 참고만 막는다.
- **[요약의 정확도]** 요약은 모델이 만든다. 원문 문장을 그대로 옮기는 경우를 막는 규칙이 있지만 완벽하지 않다. → 요약 깊이도 공개 등급의 일부로 보고, 민감 맥락은 장·관리자에게도 제목만 보인다.
- **[조직도가 없을 때]** 조직도에 없는 사람은 어느 범위에도 들지 않는다. 팀 맥락 공유는 조직도를 채운 회사에서만 동작한다.

## Open Questions

- 감사용 원문 열람: 법적 사유로 관리자가 허락 없이 원문을 봐야 할 때. 이중 승인과 주인 즉시 알림으로 둘지, 두지 않을지.
- 장의 요약 보기를 회사 설정으로 끌 수 있게 할지.
- 퇴사·이동한 사람의 맥락을 장에게 넘길지, `private` 는 지울지.
- 위 RLS 공백을 이번에 함께 막을지(승인 필요), 나머지 `pro_` 표 57개는 별도 작업으로 할지.
