## 결정

1. **정책이 진실, 주인 규칙은 그 안에서.** 정책 결정(PDP)과 주인 규칙을 합치는 규칙: 차단 → 거절, 승인 필요 → 주인에게 묻기, 그 밖 → 주인 규칙. 관리자가 「민감 맥락은 주인이 직접 허락」을 끄면 민감 맥락도 주인 규칙을 따른다(다른 가드레일과 같다, 원장에 남는다). 정책 엔진이 답하지 못하면 닫힌 쪽(묻기).
2. **깊이 판정은 원장을 거치지 않는다.** 누가 무엇을 지금 보나(depthOf)는 턴마다 부르는 빠른 길이라 규칙 그대로 두고, 원장은 요청(허락의 생애)만 기록한다.
3. **주제 목록은 정책의 일부.** 「민감할 수 있는 주제는 자동 허용하지 않음」의 `topics` 로 두어, 결정과 제안이 같은 목록을 쓴다. 끄면 제안도 멈춘다. 패턴은 저장할 때 컴파일·길이(300자)를 검사.
4. **원장의 승인자 「맥락 주인」.** 승인자를 역할로 찾지 않고 그 맥락의 주인이 홈 카드에서 정한다. 원장에서 승인하면 실행할 행위가 없으니 승인 단추를 행위가 보관된 결정에만 둔다(일반 규칙).
5. **원장에 내용을 남기지 않는다.** 사실은 민감 표시·주제 이름·관계·깊이·주인 규칙뿐, 민감할 수 있으면 제목을 가린다. 요청자 응답에는 주제 이름을 주지 않는다.
6. **같은 요청 판별은 임베딩 + 모델.** bge-m3 만으로는 「고객 B ↔ 고객 C」 0.919, 「이번 주 ↔ 지난주 회의록」 0.949, 「표 ↔ 그래프」 0.905 로 다른 요청을 같다고 본다. 임베딩으로 좁히고(턴 0.8, 맥락 글 0.6), 게이트웨이 모델(생각 끔)이 같은 결과물인가·이전 답이 아직 쓸 만한가를 한 번에 판단. 모델이 답하지 못하면 묻지 않는다(그냥 에이전트로) — 잘못 막는 것보다 한 번 더 만드는 쪽이 낫다.
7. **보이는 것만으로 매긴다.** 자동 참고의 요청 후보와 같은 원칙: 원문 깊이가 아닌 맥락은 요청 문장으로 매기지 않는다(요약 깊이의 요청 유형 예문도 쓰지 않는다).
8. **참조만.** 「그 답 보기」는 카드에 답을 담지 않고 그때 깊이로 다시 읽는다 — 회수되면 볼 수 없고, 팀원의 원문을 보면 본 기록에 남는다.
9. **참고해서 다른 것, 고쳐 달라는 것은 같은 요청이 아니다.** 영상을 찍다 두 번 잘못 막았다 — 「팀 성과급 기준을 참고해서 보상 원칙 써 줘」(팀원의 요약 깊이 맥락과 같다고 봄), 「…영업 지원 직군 기준까지 넣어 다시 정리해 줘」(어제 한 초안 요청과 같다고 봄). 판별 모델 지시에 두 경우를 적고 사례로 넣었다(판별 사례 15).
10. **다시 시켜 보기.** 30분 안에 바로 앞과 같은 문장을 보내면 묻지 않는다(처음엔 시간 조건이 없어 어제 한 같은 요청을 다시 시켜 보기로 잘못 봤다 — 시험에서 잡음).
