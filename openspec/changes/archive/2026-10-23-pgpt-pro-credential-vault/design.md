## Context

pgpt-pro 는 hark.com 의 UX 를 모방한 Vue 앱과, process-gpt 백엔드(deepagents, completion, Supabase)를 재사용하는 BFF 로 이루어져 있다. 브라우저 에이전트는 BFF 안에서 사용자별 Chromium 프로필을 띄우고, 번호가 매겨진 페이지 요소 위에서 모델이 도구를 하나씩 호출하는 루프로 동작한다. 보관함은 BFF 가 소유하고 같은 Supabase 데이터베이스의 `pro_vault_*` 테이블에 저장한다.

hark pro 벤치마크에서 확인한 사용자 경험:

- 로그인이 필요하면 채팅에 "Enter your X credentials and we'll save them to your encrypted vault." 카드가 뜨고, 하단에 "보안 제공" 표기가 붙는다. 저장하면 "✓ X 로그인 저장됨" 칩으로 바뀐다.
- 같은 아이디로 계정이 둘이면 어떤 계정으로 로그인할지 고르는 카드가 뜬다.
- "이 단계에는 당신만 아는 값이 필요해요" 형태로 일회용 값을 요청한다.
- 설정 > 계정(보관함)에 "사이트에서 이 비밀번호를 거부했습니다" 같은 상태가, 설정 > 지갑에 카드가 있다.

## Goals / Non-Goals

**Goals:**

- 비밀 값이 모델·채팅 화면·API 응답·로그·데이터베이스 평문 어디에도 나타나지 않는다.
- 데이터베이스 덤프만으로는 아무것도 복원할 수 없다(KEK 가 데이터베이스 밖에 있다).
- 키 교체가 데이터 손실이나 서비스 중단 없이 가능하다.
- 사용자·운영자가 "봉투 암호화로 저장되고 있다"를 값 노출 없이 확인할 수 있다.
- hark pro 의 로그인 카드·계정 선택·일회용 값·계정/지갑 화면을 같은 흐름으로 제공한다.

**Non-Goals:**

- 외부 KMS/HSM(AWS KMS, GCP KMS, Vault Transit) 연동. 키링 공급원은 교체 가능한 형태로 두고 이번에는 파일/환경 변수만 제공한다.
- PCI DSS 인증 범위의 카드 처리. 카드는 사용자 본인 결제 대행 용도로만 보관한다.
- process-gpt 핵심 프론트엔드/서비스에 보관함을 추가하는 일.

## Decisions

### 1. 봉투 암호화: KEK → 사용자별 DEK → 항목

- 항목은 사용자별 32바이트 DEK 로 AES-256-GCM 암호화한다. 저장 형식은 `base64(iv12 | tag16 | ciphertext)`.
- DEK 는 KEK 로 같은 방식으로 감싸 저장한다. KEK 는 데이터베이스에 두지 않는다.
- AAD 로 항목은 `item:<user>:<kind>:<site>`, DEK 는 `dek:<user>`(버전 2 이상은 `:v<n>`)를 쓴다. 암호문을 다른 사용자·종류·사이트 행으로 옮기거나 예전 버전의 감싼 DEK 로 바꿔치기하면 인증 단계에서 실패한다.
- 대안: 항목마다 DEK. 키 교체 비용과 키 테이블 크기가 커지고 사용자 단위 폐기(crypto-shredding)의 이점이 같으므로 사용자별 DEK 를 택했다.

### 2. 키링과 교체

- KEK 식별자는 SHA-256 앞 12자리. 키링은 현재 KEK 와 폐기 예정 KEK 를 함께 가진다.
- KEK 교체는 새 KEK 를 현재 키로 만들고 모든 DEK 를 다시 감싼다. 항목 암호문은 바뀌지 않는다. 폐기 KEK 아래 남은 DEK 는 다음에 열릴 때 현재 KEK 로 다시 감싼다(지연 재래핑). 아무 DEK 도 참조하지 않는 폐기 KEK 만 정리한다.
- DEK 교체는 한 트랜잭션 안에서 새 DEK 로 모든 항목을 재암호화하고 버전을 올린다.
- 공급원이 환경 변수이면 서버가 키를 쓸 수 없으므로 교체 명령은 거절하고 운영 절차(새 키를 `PRO_VAULT_KEK`, 옛 키를 `PRO_VAULT_KEK_RETIRED` 로 옮긴 뒤 재래핑)를 안내한다.
- 기존 단일 키 파일은 첫 기동 때 키링의 1번 키로 가져온다. 기존 DEK 의 AAD 는 바꾸지 않아 업그레이드 후에도 그대로 열린다.

### 3. 여러 계정·카드 구분: 구분 지문

- (종류, 아이디 또는 카드 번호)를 DEK 에서 HKDF 로 파생한 키로 HMAC 한 값을 구분 지문으로 저장한다. 평문 아이디·번호 없이도 "같은 계정이면 갱신, 다른 계정이면 새 항목"을 판단한다.
- 지문은 DEK 에 의존하므로 DEK 교체 때 다시 계산한다.

### 4. 직접 제어 중 입력 감지(`captured`)

- 페이지마다 주입되는 감시 스크립트가 제출 시점(submit, 제출 버튼 클릭, Enter)에 비밀번호/카드 입력란을 읽어 서버 바인딩으로 넘긴다. 보관함이 채운 값은 요소에 기억해 두었다가 다시 보고하지 않는다.
- 서버는 받은 즉시 암호화해 `captured` 로 저장한다. 평문은 메모리에만 잠깐 있다. 이미 저장된 값과 같으면 아무것도 하지 않는다. 다른 값이면 지문 뒤에 `:captured` 를 붙여 확인된 항목 옆에 따로 두고, 사용자가 확인하면 기존 항목을 대체한다.
- `captured` 항목은 브라우저 작업에 자동으로 쓰이지 않는다.

### 5. 모델 비노출: 네 겹

1. 페이지 스냅샷에서 비밀 입력란(password, 보관함이 채운 칸, `cc-*`, `one-time-code`, 카드/CVC/OTP 이름)은 값을 빼고 `secret:true, filled` 로만 보낸다.
2. 모델에 보내는 스크린샷은 비밀 입력란을 덮어 가린다. 실시간 화면(사용자에게 보이는 화면)은 CSS 로 글자를 점으로 바꾼다.
3. 모델의 `type` 도구는 비밀 입력란에 쓰지 못하게 거절한다.
4. 작업 중 입력한 6자 이상의 값(비밀번호, 카드 번호, 인증 코드)이 스냅샷 텍스트·도구 결과·결과 페이지 텍스트에 다시 나타나면 `[vault]` 로 바꾼다.

### 6. 사용자에게 묻는 카드는 상태보다 먼저

작업 카드를 "입력 필요"로 바꾸기 전에 보관함/선택/승인 카드를 먼저 올린다. 화면이나 자동화가 "입력 필요"를 보는 순간 무엇에 답해야 하는지가 이미 존재한다. 사용자가 답하지 않은 채 대기가 끝나면(취소, 직접 제어 완료) 카드는 `expired` 가 된다.

### 7. 승인은 별도 도구

결제·전송·삭제 직전 승인을 일반 개입(`need_user`)과 분리해 `approve` 로 둔다. 승인 카드에는 모델이 쓴 요약과 함께 서버가 아는 결제 카드 라벨(예: `Visa •••• 4242`)을 덧붙인다. 사용자는 승인/취소 한 번으로 답한다.

### 8. 검증 조회

`GET /api/vault/proof` 는 서버에서 각 항목을 실제로 열어 보고, 다른 사이트·다른 사용자 AAD, 1비트 변조, KEK 로 직접 열기가 모두 실패하는지, 행 어디에도 비밀 필드 값(평문/base64)이 없는지를 확인해 불리언으로만 돌려준다.

## Risks / Trade-offs

- [KEK 가 같은 호스트의 파일] → 데이터베이스 유출만으로는 안전하지만 서버 호스트 장악에는 취약하다. 운영 환경은 환경 변수 주입(시크릿 매니저) 또는 이후 KMS 공급원을 권장한다.
- [모델이 거부를 보고하지 않을 수 있음] → 비밀번호 거부 처리는 모델의 `login_failed` 호출에 의존한다. 보고가 없으면 사용자는 설정에서 직접 수정할 수 있다.
- [감지 휴리스틱] → 제출 시점·입력란 이름 기반이라 특이한 폼은 놓칠 수 있다. 놓쳐도 사용자는 카드/설정으로 직접 저장할 수 있고, 잘못 감지돼도 확인 전에는 쓰이지 않으며 "저장 안 함"으로 즉시 지워진다.
- [화면 가림] → 실시간 화면 가림은 CSS 에 의존하므로 페이지가 스타일을 강하게 덮으면 보일 수 있다. 모델용 스크린샷은 별도로 덮어 가린다.
- [DEK 메모리 캐시] → 성능을 위해 최대 10분 보관하고, 만료·교체 시 0으로 덮어쓴다.

## Migration Plan

1. 멱등 SQL 마이그레이션 적용(키 버전·구분 지문·메타·사용 이력 열, 활동 기록 테이블).
2. 서버 재시작: 기존 단일 키 파일이 키링 1번 키로 들어간다(식별자 동일).
3. 전수 검증 명령으로 모든 항목이 열리는지 확인하고 기존 행의 구분 지문을 채운다.
4. 되돌리기: 이전 코드로 돌아가도 기존 단일 키 파일과 v1 DEK·항목 형식이 그대로라 열린다(추가 열은 무시됨).

## Verification

- 단위/통합 테스트: 보관함(봉투 체인 독립 복호화, 비노출, AAD 바인딩, 여러 계정, 카드 검증, 감지·확인, KEK/DEK 교체 8건)과 브라우저 핸드오프(로그인 요청·거부·OTP, 카드 요청·승인, 카드 선택, 직접 제어 감지 4건). 모델 대역 서버가 모든 요청을 기록해 비밀 값이 한 번도 들어가지 않았음을 확인한다.
- UI E2E: 실제 앱과 실제 모델로 테스트 상점에서 로그인·OTP·카드 결제를 수행하고, 저장된 행을 KEK 로 독립 복호화해 사용자가 입력한 값과 일치함을, 모델 요청 기록에 비밀 값이 0건임을 확인한다. 산출물은 각 스펙 폴더의 `e2e/` 에 있다.
