## 결정

- **순서는 값 → 규칙.** 모델은 값만 내고 결정은 정책 엔진이 한다. 같은 값이면 같은 결정이고, 관리자가 규칙을 바꿀 수 있으며, 원장으로 설명할 수 있다.
- **logprob 을 서버가 바로 부른다.** 라우터의 판단 체인은 판단 모델이 먼저인데, 판단 모델은 일반 글을 확률 1.0 으로 틀려 에스컬레이션이 걸리지 않았다. 설치판에는 라우터도 기본으로 없다. 서버가 이미 쓰는 모델로 부르면 회사별 키와 사용량 기록도 그대로 따른다.
- **주제 낱말을 앞에 두지 않는다.** 앞에 두면 맥락 test 정확도가 94%에서 79%로 떨어진다. 낱말은 주제 이름과 모델 장애 때의 대체로만 쓴다.
- **주민번호 형식만 먼저 본다.** 처음에는 주민번호·계좌·전화를 모두 앞에 두었지만, 측정에서 더 잡은 것 없이 오탐만 늘었다(250건 오탐 16~17건, 주민번호만이면 11건). 계좌·전화 형식은 양식·주문번호·서명에도 걸린다. 주민번호는 모델이 놓치거나 끊겨도 사람에게 간다.
- **모델이 잠시 끊기면 묻는다.** 낱말에 안 걸리는 민감한 글이 장애 동안 자동 허용되는 것을 막는다. 확률을 주지 않는 모델은 장애가 아니라 설치의 형편이라 모두 묻지 않고 낱말로 운영한다. 민감 제안과 외부 메일에는 적용하지 않는다.
- **기준값 0.5 유지.** 0.7 이 더 나아 보이지만 사례가 뚜렷한 글이다. 실제 업무 글로 잰 뒤 정한다.
- **메일은 개인정보가 있어도 기밀 여부를 읽는다.** 승인자가 다른 별개의 질문이다.
- **필드 민감도는 그대로 둔다.** 칸 이름은 짧고 잘못 가렸을 때의 비용이 작다.

## 남은 위험
- 확률을 주지 않는 모델을 쓰는 설치에서는 낱말이 없는 민감한 글이 자동 허용된다(원장에 `regex`, 정책 화면 경고).
- 모델이 끊긴 동안의 외부 메일은 표시 낱말로만 판단한다(기록·10분 회수).
- 사례는 사람이 쓴 뚜렷한 글이다. 실제 업무 글에서 다시 재야 한다.
- 확률을 주는 모델에서만 동작한다. 다른 모델은 낱말로 돌아가고 정책 화면이 경고한다.
- `browser.payment`·`data.export`·`data.delete` 정책은 여전히 실제 동작에 연결되어 있지 않다(이번 범위 밖).
