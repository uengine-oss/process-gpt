## ADDED Requirements

### Requirement: 분기 판단 이력 기록
시스템은 워크아이템 처리 결과로 다음 경로가 결정될 때마다 그 판단을 이력으로 기록해야 한다(SHALL). 이력은 판단이 일어난 프로세스 인스턴스, 판단을 유발한 활동, 판단 주체가 된 노드(게이트웨이 또는 분기 활동)와 그 분기 유형, 그리고 최종 선택된 시퀀스와 다음 활동을 포함해야 한다(SHALL). 게이트웨이가 워크아이템을 생성하지 않는 노드라는 사실이 이력 누락의 사유가 되어서는 안 된다(SHALL NOT).

하나의 워크아이템 처리에서 여러 게이트웨이를 연속으로 통과한 경우, 각 판단 지점마다 별도의 이력을 기록해야 한다(SHALL).

#### Scenario: 배타 분기에서 한 갈래를 선택
- **GIVEN** 두 갈래로 나뉘는 배타 분기가 있는 프로세스 인스턴스가 실행 중이다
- **WHEN** 앞선 활동이 완료되어 다음 경로가 결정된다
- **THEN** 판단 주체 노드와 분기 유형, 선택된 시퀀스, 선택되지 않은 시퀀스가 이력으로 남는다
- **AND** 선택된 시퀀스가 가리키는 다음 활동이 이력에 포함된다

#### Scenario: 병렬 분기에서 모든 갈래로 진행
- **WHEN** 병렬 분기를 통과해 여러 갈래가 동시에 진행된다
- **THEN** 진행된 모든 시퀀스가 선택된 갈래로 이력에 남는다

#### Scenario: 게이트웨이를 연속으로 통과
- **WHEN** 하나의 활동 완료로 둘 이상의 게이트웨이를 연달아 통과한다
- **THEN** 게이트웨이마다 각각의 판단 이력이 남는다

#### Scenario: 조건 없는 단일 경로
- **WHEN** 분기 없이 다음 활동이 하나로 정해진다
- **THEN** 판단 방식이 무조건 진행임을 나타내는 이력이 남는다

### Requirement: 판단 방식과 근거 기록
시스템은 각 시퀀스의 평가 결과와 함께 그 결과가 어떤 방식으로 도출되었는지를 기록해야 한다(SHALL). 판단 방식은 조건식 평가, 자연어 조건에 대한 모델 판정, 기본 흐름(default flow) 선택, 무조건 진행, 우선순위에 의한 결정을 구분할 수 있어야 한다(SHALL).

조건식으로 평가한 경우 평가에 사용한 조건식 원문과 참·거짓·판정 불가를 기록해야 한다(SHALL). 모델이 판정한 경우 모델이 제시한 근거 문구를 기록해야 한다(SHALL). 조건식 평가가 오류로 실패해 다른 방식으로 대체된 경우, 실패 사실과 대체 방식을 함께 기록해야 한다(SHALL).

#### Scenario: 조건식으로 판정
- **WHEN** 시퀀스의 조건식이 평가되어 참으로 판정된다
- **THEN** 판단 방식이 조건식 평가임과 평가된 조건식 원문, 판정 결과가 이력에 남는다

#### Scenario: 자연어 조건을 모델이 판정
- **WHEN** 조건식이 없는 시퀀스의 자연어 조건을 모델이 판정한다
- **THEN** 판단 방식이 모델 판정임과 모델이 제시한 근거 문구가 이력에 남는다

#### Scenario: 조건식 평가 실패 후 대체
- **GIVEN** 시퀀스에 조건식이 지정되어 있다
- **WHEN** 조건식 평가가 오류로 실패해 다른 방식으로 결과가 정해진다
- **THEN** 조건식 평가 실패 사실과 실제로 결과를 정한 방식이 함께 이력에 남는다

#### Scenario: 참인 갈래가 없어 기본 흐름 선택
- **WHEN** 어떤 갈래도 조건을 충족하지 못해 기본 흐름으로 진행된다
- **THEN** 판단 방식이 기본 흐름 선택임이 이력에 남는다

#### Scenario: 참인 갈래가 여럿이어 우선순위로 결정
- **WHEN** 배타 분기에서 둘 이상의 갈래가 조건을 충족해 하나만 선택된다
- **THEN** 충족한 모든 갈래와, 우선순위로 결정되었다는 사실이 이력에 남는다

### Requirement: 판단 입력 스냅샷 기록
시스템은 판단에 실제로 사용한 입력 값을 이력에 함께 기록해야 한다(SHALL). 분기 노드에 참조 데이터가 지정된 경우 그 데이터가 우선 기록 대상이며, 지정되지 않은 경우 판단에 사용된 활동 출력이 기록 대상이다(SHALL).

입력 스냅샷에는 저장 크기 상한이 있어야 하며(SHALL), 상한을 넘는 경우 이력 기록 자체를 생략하지 않고 잘렸다는 사실을 남겨야 한다(SHALL NOT omit). 스냅샷은 해당 테넌트 범위 밖에서 조회되어서는 안 된다(SHALL NOT).

#### Scenario: 분기 참조 데이터로 판단
- **GIVEN** 분기 노드에 참조할 입력 데이터가 지정되어 있다
- **WHEN** 그 데이터로 분기가 판단된다
- **THEN** 판단에 사용된 참조 데이터 값이 이력에 남는다

#### Scenario: 스냅샷이 크기 상한을 초과
- **WHEN** 판단 입력이 저장 크기 상한을 초과한다
- **THEN** 이력은 정상적으로 기록되고, 입력이 잘렸다는 사실이 함께 표시된다

#### Scenario: 다른 테넌트의 이력 조회 시도
- **WHEN** 다른 테넌트가 해당 인스턴스의 판단 이력을 조회한다
- **THEN** 조회 결과에 그 이력이 포함되지 않는다

### Requirement: 모델 판정 원문 보존
시스템은 자연어 조건 판정에 사용한 모델 프롬프트와 모델 응답 원문을 보존해야 한다(SHALL). 원문은 판단 이력 본문과 구분되는 별도 기록으로 남겨야 하며(SHALL), 어떤 판단 이력에 대응하는지 상호 참조가 가능해야 한다(SHALL).

원문 기록은 판단 이력 본문과 독립적인 보존 기간과 용량 정책을 가질 수 있어야 한다(SHALL). 원문 기록이 만료·삭제되더라도 판단 이력 본문의 선택 결과와 근거는 그대로 유지되어야 한다(SHALL).

#### Scenario: 모델 판정 원문 조회
- **GIVEN** 자연어 조건 판정으로 분기가 결정되었다
- **WHEN** 해당 판단 이력의 원문 기록을 조회한다
- **THEN** 판정에 사용된 프롬프트와 모델 응답 원문을 확인할 수 있다

#### Scenario: 원문만 만료된 경우
- **GIVEN** 판단 이력의 원문 기록이 보존 기간이 지나 삭제되었다
- **WHEN** 해당 판단 이력을 조회한다
- **THEN** 선택 결과와 근거 문구는 그대로 조회된다
- **AND** 원문이 더 이상 남아 있지 않음을 구분할 수 있다

#### Scenario: 조건식만으로 판정된 분기
- **WHEN** 모델 호출 없이 조건식만으로 분기가 결정된다
- **THEN** 원문 기록은 생성되지 않는다

### Requirement: 진행 불가와 대기 상태 구분 기록
시스템은 판단 결과를 진행, 대기, 진행 불가로 구분해 기록해야 한다(SHALL).

병합 지점에서 다른 갈래의 완료를 기다려 다음 활동을 만들지 않은 경우 대기로 기록하고, 무엇을 기다리는지 식별할 수 있어야 한다(SHALL). 조건을 충족한 갈래도 기본 흐름도 없어 다음 활동을 만들 수 없는 경우 진행 불가로 기록해야 하며(SHALL), 이 상태가 이력 없이 조용히 종료되어서는 안 된다(SHALL NOT).

#### Scenario: 병합 지점에서 다른 갈래 대기
- **GIVEN** 병렬 분기의 두 갈래 중 하나만 완료되었다
- **WHEN** 완료된 갈래가 병합 지점에 도달한다
- **THEN** 판단 결과가 대기로 기록되고 기다리는 대상을 확인할 수 있다

#### Scenario: 갈 수 있는 갈래가 없음
- **GIVEN** 배타 분기의 어떤 갈래도 조건을 충족하지 못하고 기본 흐름도 지정되어 있지 않다
- **WHEN** 다음 경로가 결정된다
- **THEN** 판단 결과가 진행 불가로 기록된다
- **AND** 평가된 모든 갈래와 각각의 판정 결과가 함께 남아 원인을 확인할 수 있다

### Requirement: 재실행 회차별 이력 누적
시스템은 동일 활동이 재실행되어 분기가 다시 판단될 때 이전 판단 이력을 덮어쓰거나 삭제해서는 안 되며(SHALL NOT), 새 이력을 추가해야 한다(SHALL). 각 이력은 어느 재실행 회차의 판단인지 식별할 수 있어야 한다(SHALL).

같은 활동에 대한 이력이 여러 건인 경우, 판단 시각 순서로 정렬해 회차별 판단 변화를 추적할 수 있어야 한다(SHALL).

#### Scenario: 반려 후 재실행으로 다른 갈래 선택
- **GIVEN** 어떤 활동이 이미 한 번 판단되어 A 갈래로 진행했다
- **WHEN** 그 활동이 재실행되어 이번에는 B 갈래로 진행한다
- **THEN** A 갈래 판단 이력과 B 갈래 판단 이력이 모두 남는다
- **AND** 각 이력이 어느 회차의 판단인지 구분된다

#### Scenario: 하위 프로세스 실행 범위 구분
- **WHEN** 반복 실행되는 하위 프로세스 안에서 같은 분기가 여러 번 판단된다
- **THEN** 각 이력이 어느 실행 범위의 판단인지 구분된다

### Requirement: 판단 이력 조회
시스템은 프로세스 인스턴스 단위와 워크아이템 단위로 판단 이력을 조회하는 수단을 제공해야 한다(SHALL). 인스턴스 단위 조회 결과로부터 그 인스턴스에서 실제로 지나간 시퀀스 집합을 확정할 수 있어야 한다(SHALL).

판단 이력이 기록되면 해당 인스턴스를 관찰 중인 클라이언트가 별도 재조회 없이 변경을 인지할 수 있어야 한다(SHALL).

판단 이력이 없는 과거 인스턴스에 대해서는 조회 결과가 비어 있어야 하며, 오류로 응답해서는 안 된다(SHALL NOT).

#### Scenario: 인스턴스의 지나간 경로 확정
- **GIVEN** 여러 게이트웨이를 통과한 프로세스 인스턴스가 있다
- **WHEN** 그 인스턴스의 판단 이력을 조회한다
- **THEN** 실제로 지나간 시퀀스 집합을 확정할 수 있다
- **AND** 선택되지 않은 갈래의 시퀀스는 그 집합에 포함되지 않는다

#### Scenario: 진행 중 실시간 반영
- **GIVEN** 클라이언트가 실행 중인 인스턴스를 관찰하고 있다
- **WHEN** 새 분기 판단이 기록된다
- **THEN** 클라이언트가 재조회 없이 새 판단을 인지한다

#### Scenario: 이력이 없는 과거 인스턴스
- **WHEN** 기능 도입 이전에 실행된 인스턴스의 판단 이력을 조회한다
- **THEN** 빈 결과가 반환된다

### Requirement: 이력 기록 실패 격리
시스템은 판단 이력 기록이 실패하더라도 프로세스 진행을 중단하거나 분기 결과를 바꿔서는 안 된다(SHALL NOT). 기록 실패는 별도로 관측 가능해야 한다(SHALL).

판단 이력 기록은 다음 활동 워크아이템 생성보다 앞서 프로세스 진행을 지연시켜서는 안 된다(SHALL NOT).

#### Scenario: 이벤트 저장 실패
- **GIVEN** 이벤트 저장소가 일시적으로 응답하지 않는다
- **WHEN** 분기 판단이 일어난다
- **THEN** 다음 활동 워크아이템은 정상적으로 생성된다
- **AND** 이력 기록 실패가 관측 가능한 신호로 남는다

#### Scenario: 진행 지연 없음
- **WHEN** 판단 이력 기록이 지연된다
- **THEN** 다음 활동 워크아이템 생성이 그 지연에 묶이지 않는다
