## Context

전략 서비스(services/strategy)는 Strategy-Process-Resource-Skill 4개 레이어의 온톨로지 그래프를 보유하고 있고(`strategy_graph-store`, `strategy_strategy-map-graph`, `strategy_ontology-sync`), 이를 조회하는 API로 범용 서브그래프 브라우징(`GET /api/ontology/graph`, `GET /api/ontology/nodes/{node_id}/neighbors`)과 KPI/전략 기준 역방향 원인 추적(`GET /api/impact/kpi/{kpi_id}`, `GET /api/impact/strategy/{strategy_id}`)을 제공한다. 그러나 "이 프로세스가 어떤 전략에 기여하고, 누구와 협업하며, 어떤 스킬이 관련되는가"를 프로세스 쪽에서 묻는 총체적 조회는 없다. 그래프에는 이미 Process→KPI 방향의 `IMPACTS_KPI`, KPI→전략목표의 `HAS_KPI`, 전략 계층의 `HAS_SUB_STRATEGY`, 프로세스 구성의 `CONTAINS_TASK`, 수행 관계 `PERFORMS`, 스킬 관계 `USES_SKILL`이 존재하므로, 새 스키마 없이 기존 관계의 순회만으로 이 조회를 만들 수 있다. 전략목표·KPI 노드의 전략적 중요도(`importance`, 1~5, 기본값 3)는 `strategy-contribution-attribution` 변경에서 이미 도입되어 정렬 기준으로 재사용할 수 있다.

실행 엔진(services/deepagents)은 실행 중인 프로세스 인스턴스의 테넌트 id·프로세스 정의 id 같은 맥락을 이미 내부적으로 보유하고, 실행마다 시스템 프롬프트를 동적으로 조립하며(조건부 섹션 추가 선례 다수), 서브에이전트가 구성된 최상위 에이전트에게는 "서브에이전트 위임 규칙" 안내 블록을 조건부로 추가한다. 별도의 "메인 에이전트" 역할 구분은 코드에 없으며, 서브에이전트가 구성된 최상위 에이전트가 곧 애드혹 프로세스의 메인 에이전트 역할을 한다.

중요한 제약: 이 실행 엔진에서 프롬프트 문구만으로 새 기능(스킬) 사용을 유도했을 때 트리거 신뢰도가 낮았던 선례가 있다. 따라서 "메인 에이전트는 서브태스크 분해 전에 온톨로지를 참고할 의무가 있다"는 요구를 프롬프트 지시로 구현하면 의무 이행이 LLM의 순응에 의존하게 되어 보장이 없다.

## Goals / Non-Goals

**Goals:**
- 프로세스 정의 하나로 기여 전략·KPI(중요도 순), 협업 리소스, 관계 프로세스, 관련 스킬을 한 번에 얻는 통합 조회를 만든다.
- 프로세스 맥락이 있는 모든 에이전트 실행에서, 서브태스크 분해·작업 수행이 시작되기 전에 전략 브리핑이 이미 컨텍스트에 존재하게 한다 — 의무를 엔진 코드로 구조화한다.
- 브리핑 범위를 넘는 심층 탐색(다른 프로세스 비교, 노드 이웃 확장, 기획 단계 시뮬레이션)을 위한 에이전트 도구를 제공한다.
- 온톨로지 조회 실패가 에이전트 실행을 절대 막지 않게 한다.

**Non-Goals:**
- 온톨로지 그래프 스키마(노드/관계 종류) 확장은 하지 않는다. 기존 레이어·관계만 재사용한다.
- 전략적 중요도(가중치) 산정 로직은 다루지 않는다. 이미 존재하는 `importance` 값을 읽기만 한다.
- 에이전트가 브리핑·조회 결과를 근거로 자동으로 리소스를 재배분하거나 프로세스를 변경하는 실행 기능은 만들지 않는다 — 판단과 실행은 에이전트(및 사람)의 몫이다.
- 온톨로지 동기화(ETL) 주기나 최신성 보장은 기존 `strategy_ontology-sync` 그대로 따른다.

## Decisions

- **push(브리핑 주입)와 pull(탐색 도구)의 2계층으로 나눈다.** 순수 도구 방식은 의무 이행이 LLM 순응에 의존하고, 순수 주입 방식은 주입 범위 밖 탐색이 불가능하다. 주입으로 의무를 구조화하고 도구로 유연성을 보완하는 하이브리드가 두 약점을 모두 피한다. (대안: 도구+프롬프트 지시만 — 기각, 신뢰도 선례 때문. 대안: 주입만 — 기각, 기획 단계·비교 탐색 불가.)
- **전략 서비스에 통합 엔드포인트 `GET /api/ontology/process/{proc_def_id}/strategic-context` 하나를 신설한다.** 기여 전략·KPI, 협업 리소스, 관계 프로세스, 관련 스킬을 한 응답으로 반환한다. 브리핑 주입(엔진)과 탐색 도구(에이전트)가 같은 엔드포인트를 쓴다. 파편 API 여러 개(기여도 전용 + 이웃 확장 조합)를 클라이언트가 조립하는 설계는 기각 — 실행당 호출 수가 늘고, "총체적 조회"라는 요구와 어긋난다. 경로는 진단 성격의 `/api/impact/*`가 아니라 조망 성격의 `/api/ontology/*` 아래에 둔다.
- **그래프 순회는 기존 관계를 프로세스 루트로 조합한다.** 기여: Process --(IMPACTS_KPI)--> KPI --(소속 전략목표)--> 상위 전략목표(재귀). 협업: Process --(CONTAINS_TASK)--> Task <--(PERFORMS)-- User/Agent. 스킬: Task/수행 Agent --(USES_SKILL)--> Skill. 관계 프로세스: 같은 KPI에 기여(`IMPACTS_KPI`)하거나 같은 리소스가 수행하는 다른 Process. 모든 목록은 결정적으로 정렬하고, 기여 전략은 `importance` 내림차순(값이 없으면 기본값 취급 + 그 사실을 응답에 표시)으로 정렬한다.
- **동기화 대기와 "연결 없음"을 구분한다.** 프로세스 정의가 플랫폼에는 있으나 그래프에 아직 없으면 `sync_pending=true`와 빈 목록을, 그래프에 있는데 연결이 없으면 `sync_pending=false`와 빈 목록을 반환한다. 플랫폼에도 없으면 404.
- **브리핑 주입은 프로세스 맥락이 있는 모든 실행에 적용한다.** 애드혹(서브에이전트 보유) 실행에만 주입하는 안은 기각 — 일반 워크아이템 처리도 전략 맥락을 알면 수행 품질·우선순위 판단이 달라지고, 브리핑을 압축하면 토큰 부담이 크지 않다. 엔진이 에이전트 구성 시점에 통합 엔드포인트를 짧은 타임아웃으로 호출하고, 결과를 사람이 읽는 압축 요약(기여 전략 상위 N개 + 중요도, 협업 대상·관계 프로세스·스킬 이름 목록)으로 시스템 프롬프트에 추가한다. 조회 실패·타임아웃·빈 결과면 브리핑 섹션 없이 실행을 계속한다(fail-open).
- **애드혹 메인 에이전트의 의무는 "주입 + 반영 지침"으로 구조화한다.** 서브에이전트가 구성된 실행에서는 기존 "서브에이전트 위임 규칙" 블록에 "위 전략 브리핑의 관계 프로세스·에이전트·스킬을 서브태스크 위임 계획에 반영하라"는 지침을 추가한다. 온톨로지 "조회" 자체는 엔진이 이미 수행했으므로 LLM이 생략할 수 없고, LLM에게 남는 것은 반영뿐이다 — 기존 설계(호출 자체를 프롬프트로 지시)보다 의무의 보장 수준이 근본적으로 높다.
- **탐색 도구는 2개를 제공한다.** (1) 전략 컨텍스트 조회 도구 — 통합 엔드포인트를 감싸며, 프로세스 정의 id를 선택 인자로 받고 생략 시 현재 실행 맥락의 프로세스를 자동 사용한다(기존 실행 맥락 자동 활용 도구들과 같은 방식). 실행 맥락도 인자도 없으면 실패가 아니라 지정 안내를 반환한다. (2) 온톨로지 이웃 탐색 도구 — 기존 `GET /api/ontology/nodes/{node_id}/neighbors`를 감싸 임의 노드에서 관계를 따라가는 자유 탐색을 지원한다. 기존 전략 도구들과 동일하게 HTTP 오류를 예외로 던지지 않고 오류 정보를 담은 결과로 반환한다.
- **모든 테넌트·모든 에이전트에 기본 제공한다.** 온톨로지 조회는 읽기 전용이고 부작용이 없으므로 테넌트별 게이팅 없이 항상 도구 목록에 포함하고, 브리핑 주입도 전 테넌트에 적용한다.

## Risks / Trade-offs

- [브리핑 조회가 실행 시작 지연을 만든다] → 짧은 타임아웃(수 초)으로 제한하고, 실패·초과 시 브리핑 없이 즉시 진행한다(fail-open). 브리핑은 최선 노력(best-effort)이고 실행의 전제조건이 아니다.
- [브리핑이 프롬프트 토큰을 상시 소비한다] → 항목 수 상한(전략·협업·프로세스·스킬 각 상위 N개)과 이름·중요도 중심의 압축 표기로 억제한다. 상한으로 잘린 경우 브리핑에 "심층 탐색 도구로 더 볼 수 있다"를 명시해 잘림이 은폐되지 않게 한다.
- [전략 연결이 전혀 없는 테넌트(전략맵 미구축)는 매 실행마다 무의미한 호출이 발생한다] → 빈 결과면 브리핑 섹션 자체를 생략하고, 호출 캐시·스킵 최적화는 실측 후 후속 변경에서 다룬다.
- [관계 프로세스·협업 대상 판단이 그래프 이웃 관계에만 의존한다 — 실행 이력 통계(실제로 자주 함께 처리한 관계)는 반영되지 않는다] → 이번 범위는 그래프 관계까지로 한정하고 통계 결합은 후속 변경 후보로 남긴다.
- [순회 깊이·순환으로 응답이 느려지거나 중복될 수 있다] → 전략 상향 순회는 방문 노드 중복 제거로, 관계 프로세스·스킬 수집은 1~2홉으로 제한한다.
- ["반영 지침"까지는 여전히 프롬프트다 — 브리핑을 읽고도 위임 계획에 반영하지 않을 수 있다] → 조회 의무는 엔진이 보장하므로 최악의 경우에도 "브리핑이 컨텍스트에 있는데 활용이 미흡"까지로 축소된다. 반영 품질은 E2E 관찰로 확인하고, 미흡하면 브리핑 형식(위임 계획 템플릿화 등)을 후속으로 조정한다.

## Migration Plan

- 온톨로지 그래프 스키마 변경이 없으므로 마이그레이션·백필이 필요 없다.
- 전략 서비스의 통합 엔드포인트를 먼저 배포한 뒤 deepagents의 주입·도구를 배포한다. 순서가 바뀌어도 주입은 fail-open, 도구는 오류 결과 반환이므로 실행에 영향이 없다.
- 롤백은 신규 엔드포인트·주입 로직·도구 배포를 되돌리는 것으로 충분하며 기존 데이터에 영향이 없다.

## Open Questions

- 브리핑 항목 수 상한(N)과 타임아웃 값은 구현 중 실측으로 정한다 — 초기값으로 각 5개·3초를 제안한다.
- deepagents 실행 맥락에서 프로세스 정의 id를 얻는 경로(워크아이템 행의 필드 vs 인스턴스 조회)는 구현 시 확인한다 — 수행 이력 테이블에 proc_def_id가 있으므로 워크아이템 행에서 직접 얻을 가능성이 높다.
- 브리핑 반영 품질이 E2E에서 계속 낮게 관찰되면, 위임 도구 호출 시 브리핑 참조를 구조적으로 요구하는 형식(위임 사유 필드 등)을 후속 변경으로 검토한다.
