## Context

전략(Strategy)-KPI-프로세스(Process)-태스크(Task)-리소스(User/Agent)-스킬(Skill)로 이어지는 온톨로지 그래프(Apache AGE 기반)와, 이 그래프를 역추적해 KPI 이상의 원인과 개선 대상 스킬을 찾는 조회(`strategy_impact-analysis`), 그리고 사람/에이전트 실행 이력을 담은 별도의 분석 스타 스키마(`analytic-service_dashboard-analytics`)가 이미 존재한다. 다만 이 세 축은 각자 다른 질문에 답하도록 설계되어 있다: 온톨로지 역추적은 "이 KPI가 왜 미달했는가"를, 분석 대시보드는 "에이전트와 사람의 실행 통계가 어떻게 다른가"를 다룰 뿐, "전략적 중요도로 가중했을 때 각 성과자(에이전트·사람)가 전체 전략에 얼마나 기여했는가"와 "사람이 에이전트의 스킬을 얼마나 성장시켰는가"라는 두 질문에는 답하지 못한다. 또한 전략/KPI 노드에는 아직 "전략적 중요도(가중치)" 개념이 없어 여러 전략 목표에 걸친 기여도를 하나의 점수로 합산할 근거가 없다.

이 변경은 기존 그래프·분석 인프라를 재사용하면서, 그 위에 (1) 중요도 가중 기여도 집계, (2) 스킬 기여자 이력, (3) 이를 묶은 대시보드 뷰를 추가한다.

## Goals / Non-Goals

**Goals:**
- 전략맵의 전략 목표·KPI에 전략적 중요도(가중치) 속성을 추가한다.
- 전략/KPI 관점(하향)과 성과자(에이전트·사람) 관점(상향) 양방향으로, 중요도 가중 기여도를 조회할 수 있게 한다.
- 사람과 에이전트를 하나의 "성과자" 개념으로 동일한 응답 스키마에서 함께 다룬다.
- 스킬 단위로 어떤 사람이 얼마나 기여(생성·수정·제안 승인)했는지 이력을 남기고 조회할 수 있게 한다.
- 위 데이터를 결합해 전략 중요도 순으로 정렬된 성과·성장 기여도 대시보드 뷰를 제공한다.

**Non-Goals:**
- KPI 미달 원인 진단이나 병목 프로세스 탐지 로직 자체를 새로 만들지 않는다(`strategy_impact-analysis`를 그대로 재사용).
- 전략적 중요도를 자동으로 산정하는 알고리즘(재무 기여도 기반 자동 가중치 산출 등)은 이번 범위에서 다루지 않는다 — 최초 버전은 수동 입력값을 그대로 사용한다.
- 개인별 보상·평가(HR 성과평가)로의 연동은 다루지 않는다. 이 변경은 조회·집계 뷰까지만 제공한다.

## Decisions

**1. 중요도(가중치)는 Strategy/KPI 노드의 정수 속성(1~5)으로 둔다.**
0.0~1.0 정규화 값 대신 1~5 정수 등급을 택했다. 경영진이 다루는 BSC 우선순위는 보통 "매우 낮음~매우 높음" 같은 서수 등급으로 입력되며, 정규화된 소수는 합산 시 재정규화 로직이 추가로 필요해 MVP에는 과도하다. 조회 시점에 필요하면 정수 등급을 0~1 스케일로 환산해 가중합을 계산한다.

**2. 기여도 점수는 `strategy_impact-analysis`가 이미 계산하는 실행 지표 기반 기여 랭킹을 재사용하고, 그 위에 중요도 가중합만 추가한다.**
"성과자가 KPI에 얼마나 기여했는가"를 새로 정의하지 않고, 기존 역추적 조회가 산출하는 태스크·리소스 단위 실행 지표(수행 건수, 평균 처리시간, KPI 달성 기여도)를 재사용한다. 새 기여도 조회는 이 값을 KPI가 속한 전략의 중요도로 가중해 여러 KPI에 걸쳐 합산하는 집계 계층만 추가한다. 기여도 산정 로직을 이원화하면 두 조회의 결과가 어긋날 위험이 있어 단일 소스를 유지한다.

**2-1. 기여도는 KPI를 실제로 측정한 "그 프로세스 인스턴스 집합"에만 스코프를 맞춘다 — 프로세스 정의 전체의 누적 실행 이력을 쓰지 않는다.**
`strategy_kpi-measurement`가 KPI `current_value`를 산출할 때 실제로 집계 대상으로 삼은 완료 인스턴스(측정 유형에 따라 `instance_count`/`avg_duration_hours`/`form_value_sum`이 참조하는 인스턴스 집합)를 기여도 계산의 기준 모집단으로 그대로 재사용한다. 같은 프로세스 정의를 실행했더라도 그 측정 시점/기간에 포함되지 않은 인스턴스(예: 측정 이후 실행되었거나 실패·중단된 인스턴스)의 수행자는 그 KPI의 기여자로 잡히지 않아야 한다 — 그렇지 않으면 "이 사람/에이전트가 이 KPI 실적에 실제로 기여했다"는 명제가 깨진다. `form_value_sum` 유형은 인스턴스 단위로 기여 비중을 배분해야 하므로(수행자가 다른 두 인스턴스의 폼 값이 다르면 기여도도 달라짐), 프로세스 단위 평균 지표만으로는 이 요구를 충족할 수 없다 — 인스턴스·태스크 단위 원본 실행 기록(분석 서비스의 `fact_task`/`fact_process_instance` 또는 이에 준하는 워크아이템 이력)까지 내려가 조인해야 한다. `manual`처럼 인스턴스 실행과 무관하게 값이 입력되는 KPI, 또는 응답자를 식별할 수 없는 `survey_score`는 애초에 인스턴스-성과자 연결이 존재하지 않으므로 기여도 대신 추적 불가 상태를 반환한다.

**3. 사람과 에이전트는 그래프의 `User`/`Agent` 라벨과 관계형 `users.is_agent` 플래그를 그대로 사용하고, 응답에서 `performer_type`(`HUMAN`|`AGENT`) 필드로만 구분한다.**
별도의 통합 "성과자" 테이블이나 노드 라벨을 새로 만들지 않는다. 이미 사람과 에이전트가 같은 `users` 테이블과 그래프 리소스 레이어를 공유하므로, 새 캐패빌리티는 기존 구분 플래그를 조회 시점에 매핑하기만 하면 된다.

**4. 스킬 기여 이력은 (a) agent-feedback 서비스의 관계형 이력 테이블에 원본 이벤트로 적재하고, (b) 같은 온톨로지 그래프에 `User -CONTRIBUTED_TO-> Skill` 관계로 반영한다.**
관계형 테이블만 두면(대안 A) 감사 이력은 남지만, 전략 대시보드가 "이 스킬이 어떤 전략에 연결되는가"를 조회할 때 그래프와 별도 데이터베이스를 조인해야 한다. 그래프에만 두면(대안 B) 기존 `feedback_proposals`의 승인 이력(결정자, 사유)과 같은 상세 감사 정보를 담기 어렵다. 두 저장소에 이중 기록하되 관계형 테이블을 정본으로 삼고 그래프 엣지는 조회 최적화용 파생 데이터로 취급한다 — 이미 온톨로지 그래프가 `Skill` 노드와 `USES_SKILL` 관계를 갖고 있으므로 한 홉만 추가하면 전략→KPI→프로세스→태스크→리소스→스킬→기여자 경로를 하나의 그래프 순회로 조회할 수 있다.

**4-1. 기여도 UI는 별도 대시보드 화면이 아니라 전략맵 보드의 노드 상세에 통합한다 (스토리보드 승인, 2026-07-23).**
당초 계획(별도 "성과·성장 기여도" 화면)은 사용자가 "전략맵의 각 노드(카드)를 클릭해 상세에서 본다"는 방향으로 정정했다. 기존 StrategyBoard 상세 패널에 이미 KPI/실행과제 탭이 있으므로 "기여도" 탭을 추가하는 것이 새 내비게이션 없이 요구를 충족한다: (a) 보드 카드에 중요도 배지, (b) 상세 패널 기여도 탭 — analytic 결합 API(`GET /api/analytics/dashboard/contribution?strategy_id=`)를 게이트웨이 경유 한 번 호출로 성과자 가중 순위와 스킬 성장 기여자를 함께 표시(프론트가 strategy/agent-feedback 두 서비스를 직접 오케스트레이션하지 않음), (c) KPI 행 확장에 KPI 단위 기여도 블록(`GET /api/contribution/kpi/{id}`), (d) 성과자 이름 클릭 → 역방향 요약 다이얼로그(`GET /api/contribution/performer/{id}`), (e) 온톨로지 탐색기에 CONTRIBUTED_TO 관계 라벨('기여') 표시. analytic 결합 API는 소비처가 기여도 탭으로 바뀔 뿐이므로 `analytic-service_dashboard-analytics` 스펙 delta는 변경 없다. 스토리보드: `storyboard.html`.

**5. 신규 조회는 신규 엔드포인트로만 추가하고 기존 엔드포인트의 필드를 제거하지 않는다(additive-only).**
`GET /api/map`, `GET /api/impact/*`, `GET /api/analytics/*` 등 기존 계약은 유지한 채, 중요도 필드는 기존 응답에 추가만 하고 기여도/스킬 기여자 조회는 새 경로로 분리한다. 기존 화면과 통합에 회귀가 생기지 않도록 하기 위함이다.

## Risks / Trade-offs

- [Risk] `strategy_strategy-map-graph`, `strategy_impact-analysis` 등 전략 온톨로지 캡슐화가 아직 별도 변경(`strategy-graph-repository`)으로 진행 중이며 main 스펙에 병합(archive)되지 않았다 → 이 변경의 delta가 가리키는 베이스라인이 먼저 확정되어야 한다. **Mitigation**: `strategy-graph-repository` 변경을 먼저 archive한 뒤 이 변경을 적용한다. 순서가 바뀌면 두 delta를 수동으로 재조정한다.
- [Risk] 중요도 가중치를 수동 입력에 의존하면 미입력 시(기본값) 모든 전략이 동일 가중치로 처리되어 우선순위가 드러나지 않을 수 있다 → **Mitigation**: 중요도 미입력 노드는 중간값(3)으로 기본 처리하고, 대시보드에 "미설정" 표시를 남긴다.
- [Risk] 그래프(`CONTRIBUTED_TO`)와 관계형 이력 테이블의 이중 기록이 어긋나면(부분 실패) 스킬 기여자 조회 결과가 실제 승인 이력과 달라질 수 있다 → **Mitigation**: 관계형 테이블을 정본으로 삼고, 그래프 엣지 반영 실패는 재시도 큐 또는 배치 재동기화로 보정한다.
- [Risk] 전략맵 전체 기준 기여도 집계는 다수의 하위 KPI·프로세스·태스크를 순회해야 해 맵이 커질수록 응답 지연이 커질 수 있다 → **Mitigation**: 우선 온디맨드 계산으로 시작하고, 지연이 확인되면 주기적 사전 집계(materialized 캐시)로 전환한다.
- [Risk] 기여도를 KPI 측정에 실제로 포함된 인스턴스 집합으로 스코프를 좁히려면 온톨로지 그래프(AGE)와 인스턴스·태스크 단위 원본 실행 기록(분석 서비스 또는 워크아이템 이력)을 조인해야 해, 두 데이터 소스 간 스키마·테넌트 키가 어긋나면 기여자가 누락되거나 잘못 집계될 수 있다 → **Mitigation**: `strategy_kpi-measurement`가 측정 시 사용한 인스턴스 id 집합을 측정 이력에 함께 남기도록 하고, 기여도 조회는 그 인스턴스 id 집합을 조인 키로 사용한다.
- [Risk] 과거에 이미 만들어지거나 수정된 스킬은 기여 이력이 없어 소급 조회 시 기여자가 비어 보일 수 있다 → **Mitigation**: 기존 `feedback_proposals`의 `decided_by` 이력을 1회성 backfill 스크립트로 신규 이력 테이블/그래프 엣지에 이관한다.

## Migration Plan

1. `strategy_strategy-map-graph`에 중요도 속성을 추가하고, 기존 노드에 기본값(3)을 backfill한다. 기존 API 응답 필드는 그대로 두고 중요도 필드만 추가하므로 하위 호환된다.
2. agent-feedback에 스킬 기여 이력 테이블과 그래프 `CONTRIBUTED_TO` 엣지 반영 로직을 추가하고, 기존 `feedback_proposals` 승인 이력을 backfill한다.
3. strategy 서비스에 기여도 조회 신규 엔드포인트를 배포한다(기존 엔드포인트 무변경).
4. analytic-service에 성과·성장 기여도 대시보드 엔드포인트를 추가하고 프론트엔드 화면을 연결한다.
5. 롤백: 모든 변경이 additive이므로, 문제 발생 시 신규 엔드포인트 라우트 비활성화 및 신규 속성/테이블 무시만으로 이전 상태로 되돌릴 수 있다.

## Open Questions

- 전략적 중요도(가중치)는 누가, 어떤 주기로 입력/갱신하는가? (최초 버전은 전략 목표 편집 화면에서의 수동 입력을 전제)
- "에이전트 성장 기여" 점수는 승인된 스킬 변경 건수를 단순 합산할지, 승인 이후 그 스킬의 실제 사용 빈도·효과까지 반영할지 — 최초 버전은 건수·비중 기반 단순 집계로 시작하고 이후 확장한다.
- 사람이 여러 테넌트에 걸쳐 활동하는 경우 기여도 집계 범위를 테넌트별로 격리할지 전체 합산할지 결정이 필요하다(최초 버전은 테넌트별 격리를 기본으로 한다).
- ~~KPI 측정에 반영된 인스턴스 집합을 `strategy_kpi-measurement`가 측정 이력에 인스턴스 id 목록으로 명시적으로 남겨야 하는지~~ → **해결**: 구현 과정에서 확인한 결과, `measurement.compute_kpi_value`는 이미 `proc_def_id` + `status='COMPLETED'` + `is_deleted=false` + KPI 자체의 `period_start`/`period_end` 필터로 인스턴스 집합을 결정론적으로 산출하고 있어, 새 저장소나 측정 이력 변경 없이 조회 시점에 동일 필터로 인스턴스 집합을 재도출할 수 있었다(`contribution.py:_kpi_instance_ids`가 이 필터를 재사용). 이 과정에서 `measurement._period_filter`의 `:period_end::date` 캐스팅이 SQLAlchemy 바인드 파라미터 파싱과 충돌해 `period_end` 필터가 항상 무시되던 기존 버그를 발견해 `cast(:period_end as date)`로 수정했다(회귀 테스트 `test_instance_count_respects_period_end_boundary` 추가).
