# 브라우저 에이전트 자격 증명 대리 처리 명세

## Purpose
pgpt-pro 브라우저 에이전트가 로그인·결제 카드·일회용 인증 코드를 요구하는 페이지를 만났을 때, 시스템이 채팅 카드로 사용자에게서 값을 대신 받아 보관함에 넣고(일회용 값은 저장하지 않음) 서버에서 직접 입력하며, 그 값이 AI 모델에 전달되지 않음을 보장한다. 비밀번호 거부, 여러 항목 중 선택, 결제 승인, 직접 제어 중 입력 감지를 함께 다룬다.

## Requirements
### Requirement: 로그인 요구를 시스템이 대신 받아 보관함에 저장
브라우저 에이전트가 로그인 입력란을 채워야 하는데 그 사이트의 저장된 로그인이 없으면, 시스템은 작업을 멈추고 채팅에 보관함 카드(`kind: login`, `mode: request`, `site`, `taskId`, `state: pending`)를 먼저 올린 뒤 작업 상태를 `needs_input` 으로 바꿔야 한다(SHALL). 사용자가 카드에서 입력한 값은 `POST /api/vault`(`messageId` 포함)로 보관함에 저장되고, 카드는 `state: saved` 와 `label` 로 바뀌며, 작업은 저장된 값으로 이어서 진행해야 한다(SHALL). 사이트 비교는 정확한 호스트를 먼저, 없으면 상위·하위 도메인을 쓴다(SHALL).

#### Scenario: 처음 가는 사이트에 로그인
- **WHEN** 사용자가 "테스트 상점에 로그인해서 최근 주문을 알려줘" 라고 요청하고 에이전트가 비밀번호 입력란에 이르면
- **THEN** 채팅에 "로그인 정보를 입력하면 암호화된 보관함에 저장하고 바로 이어서 진행해요" 카드와 "보안 제공" 표기가 뜬다
- **WHEN** 사용자가 아이디와 비밀번호를 입력하고 로그인을 누르면
- **THEN** 카드는 "✓ … 로그인 저장됨" 으로 바뀌고, 상점은 올바른 비밀번호로 로그인 요청을 받는다

### Requirement: 결제 카드 요구를 시스템이 대신 받아 보관함에 저장
브라우저 에이전트가 카드 입력란(번호·만료일·CVC·소유자)을 채워야 하는데 저장된 카드가 없으면, 시스템은 채팅에 카드 등록 카드(`kind: card`, `mode: request`)를 띄워야 한다(SHALL). 사용자가 저장하면 카드 라벨(`Visa •••• 4242` 형식)이 카드에 표시되고 작업이 이어져야 한다(SHALL).

#### Scenario: 저장된 카드 없이 결제
- **WHEN** 에이전트가 결제 페이지의 카드 소유자 칸을 채우려 하고 저장된 카드가 없으면
- **THEN** 채팅에 카드 등록 카드가 뜨고, 사용자가 저장하면 "카드 저장됨 · Visa •••• 4242" 로 바뀐다
- **AND** 에이전트는 소유자·번호·만료일·CVC 를 서버에서 채운다

### Requirement: 여러 항목 중 선택
같은 사이트에 저장된 로그인이 여럿이거나 카드가 여러 장이면, 시스템은 라벨만 보이는 선택 카드(`kind: choice`, `vault: true`, `options`)를 띄워 사용자가 고르게 해야 하며(SHALL), 고른 항목을 그 작업이 끝날 때까지 다시 묻지 않고 써야 한다(SHALL). 사람이 없는 실행에서는 가장 최근에 쓴 항목을 써야 한다(SHALL).

#### Scenario: 카드 두 장 중 선택
- **GIVEN** Visa 와 Mastercard 두 장이 저장돼 있다
- **WHEN** 에이전트가 카드 입력을 시작하면
- **THEN** "저장된 카드가 여러 장이에요. 어떤 카드로 결제할까요?" 카드에 `Visa •••• 4242`, `Mastercard •••• 4444` 가 보이고
- **WHEN** 사용자가 Mastercard 를 고르면
- **THEN** 상점은 끝자리 4444 카드로 결제 요청을 받는다

### Requirement: 비밀 값을 모델에 노출하지 않는 서버 측 입력
시스템은 저장된 비밀번호·카드 번호·CVC·일회용 코드를 서버에서 페이지에 직접 입력해야 하며(SHALL), 브라우저 에이전트의 모델 요청 어디에도 이 값이 들어가지 않아야 한다(SHALL NOT). 이를 위해 페이지 스냅샷의 비밀 입력란은 값 없이 `secret: true` 와 `filled` 로만 표시하고, 모델에 보내는 스크린샷의 비밀 입력란은 가리고, 모델이 비밀 입력란에 직접 타이핑하려 하면 거절하고, 작업 중 입력한 값이 페이지 텍스트나 도구 결과에 다시 나타나면 지워야 한다(SHALL). 사용자에게 보이는 실시간 화면에서도 비밀 입력란의 글자는 가려야 한다(SHALL).

#### Scenario: 로그인·OTP·결제 전 과정의 모델 요청 검사
- **WHEN** 로그인(거부 후 갱신 포함), 일회용 코드 입력, 카드 결제를 끝까지 수행하고 모델 요청 전부를 이미지를 뺀 텍스트로 검사하면
- **THEN** 비밀번호(틀린 것과 맞는 것), 인증 코드, 카드 번호(붙여 쓴 것과 띄어 쓴 것), CVC 가 한 번도 나타나지 않는다
- **AND** 비밀 입력란은 `"secret":true` 로만 나타난다

#### Scenario: 모델이 비밀번호 칸에 직접 입력 시도
- **WHEN** 모델이 비밀번호 입력란에 일반 입력 도구로 글자를 넣으려 하면
- **THEN** 입력은 거절되고, 저장된 값 입력이나 일회용 값 요청을 쓰라는 안내가 돌아간다

### Requirement: 거부된 비밀번호의 갱신
보관함 값으로 로그인했는데 사이트가 거부하면, 시스템은 그 항목을 `rejected` 로 표시하고 갱신 카드(`kind: login`, `mode: update`, `itemId`, `label`)를 띄워야 한다(SHALL). 사용자가 새 비밀번호를 `PATCH /api/vault/:id`(`messageId` 포함)로 저장하면 상태를 비우고 다시 로그인해야 한다(SHALL). 사용자가 갱신하지 않으면 로그인을 더 시도하지 않아야 한다(SHALL NOT).

#### Scenario: 처음 입력한 비밀번호가 틀림
- **GIVEN** 사용자가 처음에 틀린 비밀번호를 저장했다
- **WHEN** 상점이 "이메일 또는 비밀번호가 올바르지 않습니다." 를 보여주면
- **THEN** 채팅에 "저장된 비밀번호를 받아들이지 않았어요" 갱신 카드가 뜨고, 설정의 계정 목록에는 "사이트에서 이 비밀번호를 거부했습니다" 가 표시된다
- **WHEN** 사용자가 새 비밀번호를 저장하면
- **THEN** 에이전트가 다시 로그인하고 상점은 올바른 비밀번호를 받는다

### Requirement: 일회용 값의 직접 전달
에이전트가 인증 코드(SMS·이메일·OTP·2FA)를 요구하는 칸을 만나면, 시스템은 일회용 값 카드(`kind: secret`, `label`)를 띄워야 한다(SHALL). `POST /api/vault/requests/:msgId/secret` 로 받은 값은 기다리던 페이지 칸에 바로 입력하고, 저장하지 않으며, 모델에 전달하지 않아야 한다(SHALL NOT). 카드는 `state: used` 가 되고 활동 기록에는 값 없이 `one_time` 이 남아야 한다(SHALL). 더 이상 기다리지 않는 요청에 값을 보내면 `409` 로 응답해야 한다(SHALL).

#### Scenario: 휴대폰 인증 코드
- **WHEN** 에이전트가 인증 코드 페이지에서 값을 요청하고 사용자가 카드에 6자리 코드를 입력하면
- **THEN** 코드가 페이지 칸에 입력돼 상점이 인증을 통과시키고, 카드는 "인증 코드 전달됨 · 저장하지 않음" 으로 바뀐다
- **AND** 보관함 항목 수는 늘지 않는다

### Requirement: 요청 닫기
사용자가 보관함 요청 카드를 닫으면(`POST /api/vault/requests/:msgId/dismiss`), 시스템은 카드를 `dismissed` 로 바꾸고 에이전트에게 값 없이 계속하거나 무엇이 부족한지 알리고 끝내라고 전달해야 하며(SHALL), 같은 요청을 다시 띄우지 않아야 한다(SHALL NOT).

#### Scenario: 로그인 요청 닫기
- **WHEN** 사용자가 로그인 카드의 닫기를 누르면
- **THEN** 카드는 "요청을 닫았어요" 로 바뀌고 작업은 로그인 없이 이어지거나 사유와 함께 끝난다

### Requirement: 직접 제어 중 입력의 감지와 보관
사용자가 실시간 화면을 직접 제어해 로그인 또는 카드 폼을 제출하면, 시스템은 제출된 값을 즉시 암호화해 `captured` 상태로 보관하고 채팅에 저장 확인 카드(`mode: capture`, `itemId`, `label`)를 띄워야 한다(SHALL). 보관함이 채운 값을 그대로 제출한 경우와 이미 저장된 값과 같은 경우에는 감지하지 않아야 한다(SHALL NOT). 사용자가 "저장"을 누르면 정식 항목이 되고, "저장 안 함"을 누르면 즉시 지워야 한다(SHALL).

#### Scenario: 다른 계정으로 직접 로그인
- **WHEN** 에이전트가 직접 로그인을 요청하고 사용자가 실시간 화면에서 `typed@shop.test` 와 비밀번호를 입력한 뒤 Enter 를 누르면
- **THEN** 채팅에 "방금 입력한 … 로그인 typed@shop.test 을 보관함에 저장할까요?" 카드가 뜬다
- **WHEN** 사용자가 저장하면
- **THEN** 그 사이트의 로그인은 기존 계정과 `typed@shop.test` 두 개가 되고, 저장된 비밀번호는 사용자가 입력한 값이다

### Requirement: 되돌릴 수 없는 단계 직전의 승인
에이전트가 결제 제출·전송·삭제 직전에 이르면, 시스템은 승인 카드(`kind: choice`, `approval: true`, `options: [승인, 취소]`)를 띄워야 하며(SHALL), 질문에는 에이전트가 쓴 요약(금액·품목)과 사용될 결제 카드의 라벨을 담아야 한다(SHALL). 사용자가 승인한 경우에만 그 단계를 수행해야 한다(SHALL).

#### Scenario: 결제 승인
- **WHEN** 에이전트가 카드 입력을 마치고 결제 버튼을 누르기 직전이면
- **THEN** "무선 이어폰 89,000원 … / 결제 카드: Visa •••• 4242" 승인 카드가 뜨고
- **WHEN** 사용자가 승인을 누르면
- **THEN** 결제가 제출되고 상점은 저장된 카드와 일치하는 카드로 결제를 받는다

#### Scenario: 결제 취소
- **WHEN** 사용자가 승인 카드에서 취소를 누르면
- **THEN** 결제는 제출되지 않고 작업은 하지 않았다는 요약과 함께 끝난다

### Requirement: 사람이 없는 실행
프로세스 단계처럼 사람이 지켜보지 않는 브라우저 실행에서는, 시스템이 로그인·카드·일회용 값·승인을 기다리지 않고 해당 단계를 건너뛰며 그 사실을 작업 메모에 남겨야 한다(SHALL).

#### Scenario: 저장된 로그인이 없는 무인 실행
- **WHEN** 무인 실행 중 저장된 로그인이 없는 사이트에 이르면
- **THEN** 보관함 카드는 뜨지 않고, 메모에 "로그인 정보가 없어 건너뜀" 이 남으며 작업은 대안 경로로 이어진다

### Requirement: 응답 없는 요청의 만료
작업이 취소되거나 직접 제어 완료 등으로 대기가 끝났는데 답이 없는 요청 카드, 그리고 서버가 다시 시작될 때 대기 중이던 보관함 카드는 `expired` 로 바뀌어야 하며(SHALL), 만료된 카드로는 값을 제출할 수 없어야 한다(SHALL NOT).

#### Scenario: 서버 재시작
- **GIVEN** 로그인 요청 카드가 대기 중이다
- **WHEN** 서버가 다시 시작되면
- **THEN** 카드는 "요청이 만료됐어요" 로 표시된다
